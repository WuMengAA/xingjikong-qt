## 一、要解决什么（先证，不猜）

审计发现（方案 §2.4）：插件通道 `ws://127.0.0.1:26789` 早在 0.6.3x 就开放了 `island_show` / `notify`，
但当时**没有任何约束**：

| 缺口 | 原状（源码证据） | 本批怎么解 |
|---|---|---|
| 报文无上限 | `onTextMessage` 先 `QJsonDocument::fromJson` 再分发（`pluginhost.cpp:139`）⇒ 一条超大 JSON 先吃满内存 | 解析**之前**按 UTF-8 字节数拒 > 64KB |
| 无频率限制 | 插件想推多少推多少；连续推送 = 岛被反复顶掉 + 历史被刷 | 每连接令牌桶 5 条/秒、突发 10 |
| 无长度限制 | 标题/正文任意长 ⇒ 胶囊/Banner 排版被撑爆 | 标题 120 码点、正文 400 码点，按**码点**截断 |
| 无来源归属 | 历史里插件推的和管理端通知长得一样；`fromAdmin` 硬编码 false | 标题加 `[插件名] ` 前缀；`fromAdmin` 仍 false（不污染"管理端置顶"） |
| 可自称紧急 | 参数里能带 `emergency:true` | 强制 false；优先级钳到 [1,8]，9-10 只给管理端 |
| 无法一键掐断 | 没有"第三方推送"总开关 | 设置页新增开关（默认**开**，理由见 §三-4） |

## 三、行为与契约变化

| 维度 | 前 | 后 | 兼容性 |
|---|---|---|---|
| 插件推岛标题 | 原样显示 | `[插件名] 原文` | 文案可见变化（**有意**：归属）；插件无需改 |
| 超长内容 | 原样 | 截断（标题 120 / 正文 400 码点） | 只影响越界内容 |
| 连发 | 原样 | 超额丢 `dropped:"rate-limited"`，仍回 `ok:true` | 插件读到 `dropped` 才知被限流 |
| `island_show` 回包 | `{ok:true}` | `+priority`、`+islandSnapshot`（注入时）、`+dropped`（丢弃时） | 只增字段 |
| `emergency` | 透传 | 强制 false（**本期岛本身还不消费该值**，见 §五-1） | — |

| 设置页 | 无此开关 | 「允许第三方推送灵动岛」默认**开** | 默认开的理由：插件通道上线以来一直放行，默认关 = 已装插件一夜失效（行为回归），治理靠四道约束而不是默认拒绝 |

### 4.2 源码契约门禁

`node Stelarith-shared-qml/scripts/test-plugin-island-gate.mjs` → **59 通过 / 0 失败**（rc=0）。
第一版曾 **假红 2 条**（把治理函数本体算进了 handleApi 段）；改成"下一个成员函数定义"定位后归零 —— 已写进脚本注释。

**负向突变（证明门禁真会报红）**：临时改 4 处源码后各跑一次门禁并逐字节还原，
4/4 全部 rc=1 且报出对应断言：

| 突变 | 门禁报出的失败 |
|---|---|
| `kRatePerSec 5 → 500` | 限流 5 条/秒（与方案 §4.5 同值） |
| `if (msg.size() > kMaxMessageBytes)` → `if (false && …)` | 超长判定是**真会生效**的 if 条件 |
| 删掉 `api.senderPriorityLimit = …` | senderPriorityLimit → AgentSettings::pluginIslandPush() |
| `m_pluginIslandPush = true → false` | agent_ui 成员默认值与 AgentSettings 同值 |

> 第 2 条是**第一轮门禁漏掉的**：原先只断言"超长判定在 fromJson 之前"，`false &&` 蒙混过关。
> 补了"判据本身真会生效"的断言后才有拦截力。这是本轮最值得记的一条。

## 五、未做 / 未验证 / 已知限制（明说）

1. **优先级本期不参与仲裁**：`priority` 只做钳制并回给插件；岛目前仍是"单任务、新内容顶旧内容"，
   真正的抢占/回落/队列是 T 档（方案 §5.1）。本批给的是**协议侧前置**，不是行为变化。
2. **开关（⑧）未作运行时验证**：原因见 §4.3；门禁能保证"接线在、键名一致、默认值一致"，
   但"关掉真的不推"需要在一个可写 QSettings 且不干扰生产的沙箱里再验一次（建议 F 盘隔离用户配置或
   临时改 `setOrganizationName` 的测试构建）。
3. **`notify` 的失败原因不透出**：`PluginAgentApi::notify` 签名是 `void`，`notifyFromParams` 的返回值
   （`exam-active-gated` / `notify-disabled-by-local-setting`）被吞掉，插件只能看到"桶放行了"。
   改签名会动对外 SDK 契约，留到 P 档协议 v2（方案 §5.2）。
4. **设置页开关未做 UI 实跑**：本批只做了 `qml` 文本改动 + 门禁断言绑定；被控端 `AgentShell` 是 QQuickWidget，
   沙箱实例是可以在屏幕上打开的，但**本轮没走界面点击**。
5. **真机 / 生产未验证**：生产实例保持运行（未重启、未替换 exe）；本批产物只在 `build/`，**未出包、未 OTA**。
6. **审计计数只进内存**：`islandGateStats()` 已实现但**尚无调用方**（没有日志出口/界面），
   等于"记了但没地方看"，属于 P 档的做事项。

## 六、踩坑（写给下一个会话）

1. **沙箱改 `LOCALAPPDATA` 有连锁反应**：`agentEnvPath()` 在 `%LOCALAPPDATA%\xingjikong` 建不出来时
   **回退到 exe 同目录**（`build/agent.env`），而程序写配置时会 `qputenv` 一堆 `STE_QT_*` 并写回该文件。
   本轮因此误生成了 `build/agent.env`（已删）。要隔离数据目录时，**先确保 `xingjikong/` 子目录可建**。
2. **同机两个被控端实例时，截图/历史文件都不能作为"哪个进程收到了"的证据**：两者都开着自己的插件口、
   各自有岛窗。最终靠"插件回包里的岛状态快照"归因 —— 这也是 `islandSnapshot` 存在的唯一理由。
3. **不能从外部杀"看起来像生产"的进程**：本轮误杀了一个沙箱实例（pid 3908，路径 `...\control-qt\build\`），
   不是生产的 `C:\Program Files\Stelarith\`。教训：进程名相同，**判断依据必须是 `Path`**。
4. **PowerShell 端跑 WebSocket 客户端不可靠**：`.NET` 的 `ReceiveAsync` 会分帧返回（`EndOfMessage=false`），
   第一版把半截 JSON 当完整消息解析；取消令牌也无法可靠打断挂起的接收。改 C# 辅助类后一次通过。
5. **xunit 式断言要盯"真会生效"**：只断言顺序（`indexOf(a) < indexOf(b)`）挡不住 `if (false && …)`。
6. **`Rebuild` 前必须停掉占用 exe 的沙箱实例**：LNK1104 的直接原因就是旧实例还跑着同一个 exe。

## 七、路径 / 接口迁移对照

| 维度 | 以前 | 现在 |
|---|---|---|
| 插件推岛入口 | `PluginAgentApi::islandShow`（无时刻、无治理） | `island_show` → `PluginHost::handleIslandShow` → `islandShowAt`（治理后） |
