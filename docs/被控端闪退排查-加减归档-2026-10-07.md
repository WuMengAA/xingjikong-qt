# 被控端闪退 · 排查与修复（2026-10-07）

> 用户报障原话：「**被控端闪退**」。
> 结论先说：**不是代码崩溃，是绿色包漏了 Qt WebEngine 的运行时资源。**
> 只要有人订阅教室画面，被控端就会在 3~5 秒内崩掉。

---

## 一、取证（没有一个结论是猜的）

### 1. 进程列表里没有被控端

只有管理端（`pkg-0.6.14\viewer-qt.exe`，用户刚装的新版）在跑。⇒ 说明被控端已经退出了。

### 2. Windows 事件日志里找到真实崩溃

`Application Error`（Id 1000）+ `Windows Error Reporting`（Id 1001），**三对**记录：

| 时刻 | 崩溃的 exe 路径 |
|---|---|
| 01:34:54 | `C:\Users\Administrator\Downloads\agent-public-0.6.5\stelarith-agent-qt.exe` |
| 01:36:29 | `D:\...\Stelarith-control-qt\dist\agent-portable-0.6.5\stelarith-agent-qt.exe` |
| 01:36:55 | `C:\Users\Administrator\Downloads\agent-portable-0.6.5\stelarith-agent-qt.exe` |

三个副本，全部崩 —— **不是某一份文件坏了，是这一版包的通病**。

崩溃详情（三条完全一致）：

```
出错应用程序名称： stelarith-agent-qt.exe
出错模块名称：     ucrtbase.dll          ← C 运行时
异常代码：         0xc0000409            ← STATUS_STACK_BUFFER_OVERRUN / __fastfail
错误偏移：         0x00000000000a527e    ← 三次同一个偏移 = 同一个确定的崩溃点
```

### 3. 用 FILETIME 算出"活了几秒"

事件里的"出错应用程序开始时间"是 Windows FILETIME，换算后：

| 崩溃时刻 | 进程启动 | **存活** |
|---|---|---|
| 01:36:55 | 01:36:49.605 | **5.4 秒** |
| 01:36:29 | 01:36:25.323 | **3.7 秒** |
| 01:34:54 | 01:34:48.874 | **5.1 秒** |

⇒ **启动三五秒就没了，这就是用户说的"闪退"。**

## 二、根因

**被控端绿色包缺少 Qt WebEngine 的三类运行时资源：**

| 缺的东西 | 大小 | 作用 |
|---|---|---|
| `resources/`（`icudtl.dat`、`qtwebengine_*.pak`、`v8_context_snapshot.bin`、`locales/`） | 23 MB | Chromium 的 ICU 数据、资源包、V8 快照 —— **没有它 WebEngine 进程起不来** |
| `translations/qtwebengine_locales/` | 约 40 KB | WebEngine 的本地化 |
| `position/` | 约 100 KB | Qt6Positioning 的插件目录（`Qt6Positioning.dll` 带了、插件却没带） |

**为什么会漏：** 绿色包是**手工拼的** —— 从 `deploy/` 素材库挑文件复制，再压 zip。
而 **`deploy/` 里根本没有 `resources/` 和 `translations/`**（这两个目录只由 `windeployqt` 产出到 `build/`）。
⇒ 手工挑的时候，**根本看不到这两个目录，自然也想不起来**。

**为什么"平时能用、一开画面就崩"：** WebEngine 的视图是**延迟创建**的
（代码注释原话：`WebEngine 已按需就绪（Chromium 进程会在首次建 view 时启动）`）。
所以被控端照常启动、照常注册、照常推 JPEG 帧；
只有"有人订阅画面 → `initRtcView()` → 建 Chromium view"那一刻才碰 `resources/` ⇒ 崩。

> ⚠️ **同一个病在管理端已经犯过一次**：0.6.0 的管理端绿色包根层缺 `resources/`，
> 只在要看远程画面时才炸。管理端后来有 `scripts/make-portable.mjs`（15 项必需件清单）兜住了，
> **而被控端一直没有打包脚本** —— 所以同样的坑又踩了一遍，而且这次直接发到了线上。

## 三、修复

### 3.1 补齐缺件并重打包

- 往包目录补：`resources/`、`translations/`、`position/`（从 `build/`）、`dxcompiler.dll`、`dxil.dll`
- 重打 `dist/stelarith-agent-portable-0.6.5.zip`：原 97,363,635 B → **125,526,273 B**（54 条目）
- 旧包**改名保留**（不是删除）：`dist/stelarith-agent-portable-0.6.5.zip.bad-缺WebEngine资源`

### 3.2 新增打包脚本（根治）

**新增文件** `Stelarith-control-qt/scripts/make-portable-agent.mjs`（约 190 行）

职责：从 `deploy/`（素材库）+ `build/`（exe 与 WebEngine 资源）组装绿色包并压 zip。

关键设计：
- **版本号唯一真源**：读 `src/main.cpp` 的 `kAppVersion`，脚本里不另抄一份；
- **`REQUIRED` 必需件清单共 29 项**，含事故漏掉的
  `resources/icudtl.dat`、`resources/qtwebengine_resources.pak`、`resources/v8_context_snapshot.bin`、
  `translations/qtwebengine_locales/en-US.pak`、`position/qtposition_nmea.dll`；
  缺任何一项 ⇒ **打包前就 fail**，产不出包；
- **`FROM_BUILD = ["resources","translations"]`** 显式标注"这两样 deploy/ 没有，必须从 build 取"
  —— 把这次事故的原因写进代码，而不是写进某人的记忆；
- **`NEVER_SHIP = ["agent.env","TEST1-NOTES.txt"]`**：
  `agent.env` 含**每机独立的真实设备令牌**，打进发布包 = 谁下载都能冒充设备；
  `TEST1-NOTES.txt` 是测试机调试笔记。（**旧包里这两个都在**，见"待办"）
- `--check <zip>` 只读检查模式（可对任意已存在的包用）。

### 3.3 修改的既有文件

**无。** 本轮没有改被控端的任何源码 —— 崩溃不在代码里，在打包产物里。

> 说明：这与"我 02:07 编过一次被控端 exe（同步 `singleinstance.cpp` 的 stderr 转码）"无关：
> 崩溃发生在 01:34–01:37，早于那次编译；而且崩溃的是**包里的** exe，不是 `build/` 里那份。

## 五、待办 / 需要决策

### 5.1（要用户拍板）教室里已装的 0.6.5 拿不到这个修复

被控端的升级判定是 `云端版本 > 本机版本` 才动作
（`src/main.cpp`：版本相同走 `升级检查：已是最新`）。这次是**同版本号换内容**，
所以已在教室机上的 0.6.5 **不会自动更新**。

要推给教室机，只有两条路：
1. **升版本号**（0.6.6）重新编译 + 出包 + 发布 ⇒ 教室机自动升级；
   ⚠️ **但代价是**：`src/main.cpp` 里压着**别人的在途工作**（考试模式、设备指纹、远程终端），
   一重编就会把这些**未完成**的代码一起发到教室机。**这个时机得由用户定**，我不擅自做。
2. 现场手动覆盖（U 盘/远程把新的 `resources/`、`translations/` 复制进去）——
   不用重编，但一台台来。

### 5.2 旧包里带出去的东西（本次未动）

- **`agent.env` 含真实设备令牌**（`STE_QT_WS_TOKEN=79b2…`）。**已经被放进过发布包和 `Downloads`**。
  ⇒ 建议：**轮换该设备的令牌**，并确认新脚本的 `NEVER_SHIP` 生效（本次已生效）。
- 包里还有 `TEST1-NOTES.txt`（测试机笔记）。
- `dist/` 下还躺着 0.6.4 的包，**同样缺 `resources/`** —— 如果还有机器装的是 0.6.4，一并处理。
