# 星集控 · Qt 线 存量包袱与上线清理方案

> 生成：2026-10-05 ｜ 范围：**仅 Qt 线（被控端/管理端/云端）** ｜ 目的：上线前把历史包袱理清、给出清理与切换清单
> 取证：云端 `/api/devices`、`Get-ScheduledTask`、`_deploy/` 目录盘点、`cl/` 文档（家底清单 / 指挥台 / 勘误）

## 〇、一句话结论

**好消息**：Qt 线在教室机上**没有任何存量**（云端设备表 `count=1`，且那 1 台是本机 TEST1）——
所以**不存在"一批要升级的旧 Qt 包"**，你原来担心的"上线后一半机器没画面"在当前事实上不成立。

**真包袱有三类**：
1. **旧代客户端残留**（ClassIsland 插件 / Rust 被控端 / Flutter 控制端）——若教室机上已有，会与 Qt 被控端**抢指令**；
2. **本机遗留物**（4 个退役计划任务、3.8GB 旧装机包、多个旧工程副本）；
3. **一个关键事实**：本机 TEST1 跑的是 **`0.4.0-v1`**，**不含 `self_update`** ——
   即**第一次升级到 0.5.0 必须重装，OTA 升不了**（见第五节）。

## 一、四代客户端与两条部署线（历史全貌）

本项目历史上做过**四代被控端**、**两条并行部署线**：

| 代 | 客户端 | 语言/形态 | 通道 | 现状 |
|---|---|---|---|---|
| 1 | Flutter 控制端 | Flutter | ? | 已弃 |
| 2 | **Rust 被控端**（`school-multimedia-control`） | Rust + NSIS 包 | 自建 WS | 退役中（G2） |
| 3 | **ClassIsland 集控插件**（`StelarithControlPlugin.cipx`） | C# / Avalonia | **CIMS-backend 8096/8097/8098/8100** | 另一条线（CIMS） |
| 4 | **Qt 被控端**（`stelarith-agent-qt.exe`） | Qt6 C++ | **cloud-ws 8788** | **当前正主** |

**两条部署线**（端口与后端完全不同，互不相通）：

```
旧线（ClassIsland/CIMS）:  教室机 ClassIsland + 插件 ──HTTP──► CIMS-backend(FastAPI 8096…)
新线（Qt）:                教室机 stelarith-agent-qt ──WS───► cloud-ws(8788) ──► viewer-qt / 网页面板
```

> ⚠️ **两条线服务的是同一批教室机**。这正是"抢指令"风险的来源：同一台机器上若同时跑着
> 旧插件（轮询 8096）与 Qt agent（连 8788），管理器会**看到两条通道都在回话**，指令可能双发。

## 三、对 Qt 线上线的具体风险

| # | 风险 | 触发条件 | 后果 | 处置 |
|---|---|---|---|---|
| R1 | **抢指令** | 教室机同时跑旧插件(8096)与 Qt agent(8788) | 管理器双通道下发，设备行为不可预期 | 装 Qt 前**先停/卸旧客户端** |
| R2 | **uid 冲突** | 两台机用同一 `uid`（如都叫 TEST1） | 云端设备表互相顶替，画面/指令串台 | 每台唯一 uid（`CLASS101-PC01`），已在部署手册约定 |
| R3 | **单例锁误判** | 见旧包/新包混装 | 新实例被旧实例锁挡（或反之） | 装机后确认只有一个 `stelarith-agent-qt.exe` |
| R4 | **发错包** | 从 `_deploy\` 拿了旧线包 | 装上 ClassIsland 插件而非 Qt agent | 只认 `dist\stelarith-agent-setup.exe` + 核对 sha256 |
| R5 | **令牌不对** | 教室机 `agent.env` 与云端不一致 | 连不上、被 AUTH_REQUIRED 拒 | 按《配置与凭据清单》成对替换 |
| R6 | **首次升级靠重装** | TEST1 当前 `0.4.0-v1` 无 `self_update` | 想升 0.5.0 时 OTA 下发无效 | 见第五节：**首升必须重装** |

## 四、上线前清理清单（按"必须/建议/不归本条线"分级）

### 4.1 必须做（否则上线会出错）

- [ ] **确认教室机上现装的是什么**（旧插件？Rust 被控端？还是全新？）——见第六节，这是唯一必须你确认的信息。
- [ ] **首台上线 = 重装**（不是 OTA）：TEST1 及任何跑 `0.4.0-v1` 的机器，必须用 0.5.0 安装包**重装**。
- [ ] 每台机 uid 唯一、令牌与云端一致。
- [ ] 装完**确认旧客户端已停**（任务管理器里只有一个 `stelarith-agent-qt.exe`）。

### 4.2 建议做（降低接手成本）

- [ ] 本机 4 个 Disabled 计划任务：导出 XML → 删除（需你点头）。
- [ ] `_deploy\` 旧线包（3.8GB）：移到 `_archive` 或外部归档，**避免分发时拿错**。
- [ ] 旧工程副本（`-旧副本-20261003` 等）：确认无用后归档。
- [ ] 建立**装机台账**（uid / 班级 / 位置 / 版本 / 装机日期 / sha256），《运维手册》已含模板位。

### 4.3 不归本条线（只登记）

- 站点旧 catch-all(A7) 删除 —— 站点线。
- ClassIsland 插件线退役节奏 —— CIMS 线。
- CIMS-backend 的 8096/8097/8098/8100 —— CIMS 线。

## 五、🔑 关键结论：第一次升级只能"重装"，OTA 要从 0.5.0 起才生效

**事实链**：

1. `self_update` 是 **0.5.0 才引入**的能力（commit `87006a1`）。
2. 云端设备表显示 **TEST1 跑的是 `0.4.0-v1`**（本机生产包，10-03 打的）。
3. 一个**没有 `self_update` 代码**的旧 exe，收到 `self_update` 指令会走到「未知动作」分支——
   **不会下载、不会安装**，OTA 对它无效。

**推论（对上线最重要的一条）**：

> **OTA 只能升级"已经具备 OTA 的版本"。**
> 所以升级路径是 **两段式**：
>
> | 阶段 | 手段 | 说明 |
> |---|---|---|
> | ① 存量 → 0.5.0 | **重装**（U 盘 / 组策略 / 远程装 NSIS 包） | 一次性，把 OTA 能力"种"进去 |
> | ② 0.5.0 → 以后每版 | **OTA**（云端下发 `self_update`） | 之后才享受"远程升级" |

**处置建议**：把 TEST1 作为**第一台重装到 0.5.0 的机器**（它就在本机，成本最低），
验证「重装 → 版本变 0.5.0 → 云端设备表 `version` 更新 → 之后 OTA 可用」这条链，
再谈教室机铺开。

## 六、需要你确认/提供的信息（只有你能答）

1. **教室机上现在装的是什么？**
   - 从来没装过（全新）→ 干净，直接装 Qt 0.5.0；
   - 装过 ClassIsland 插件 → 需先停插件再装 Qt（否则抢指令）；
   - 装过 Rust 被控端 → 需先停/卸（检查 `Stelarith-Agent-*` 类任务与进程）。
2. **有多少台教室机、分布在哪些班**（用于生成 uid 命名与台账）。
3. 是否同意清理本机 4 个 Disabled 计划任务（导出 XML 备份后删）。
4. `_deploy\` 3.8GB 旧线包：归档还是保留？

## 七、我建议的下一步（在你确认第六节后）

1. 在本机把 **TEST1 重装到 0.5.0**，验证"首升重装 + 版本上报"（10 分钟内可完成）。
2. 生成**教室机装机台账模板** + **首装/切换检查脚本**（停旧客户端 → 装 Qt → 自检）。
3. 之后教室机逐台铺开（G5 从 0% 起步），每台跑一遍检查脚本。

> 本方案**未执行任何删除或改动**：计划任务、装机包、工程副本**全部原样未动**，等你逐项点头。
