## 一、修掉的五处

### 1. `DynamicIsland.qml:73` — Row 里用了禁用锚点（**刷屏十几条**）

```
QML Row: Cannot specify left, right, horizontalCenter, fill or centerIn
anchors for items inside Row. Row will not function.
```

收起态那个"展开"文字写了 `anchors.right: parent.right`。Row 是定位器，
**子项不许自己指定横向锚点**（纵向的 `verticalCenter` 可以）。
⇒ 删除该行；横向位置交给 Row 自己排，"展开"本来就是这一行最后一个。

### 2. `Main.qml` — `ReferenceError: ntSeverity is not defined`

通知弹窗的 severity 属性挂在 `ntCol` 上（`ntCol.ntSeverity`），
**同文件另外三处都写对了，只有发送那一处漏了前缀**。
⇒ `ntSeverity` → `ntCol.ntSeverity`。

影响：发送通知时这行抛 ReferenceError，severity 传不出去。

### 3. `Main.qml` — `ReferenceError: hint is not defined`（`broadcastAll`）

```
hint("广播要给所有机器发，要管理员身份")   ← 4 处
```

`broadcastAll` 是 **root 级**函数，而 `hint()` 只住在集控页里 ⇒ 4 处全是 ReferenceError，
提示一句都出不来 —— **广播发出去了、一句回话没有**，看着跟"点了没反应"一模一样。

讽刺的是函数下面那段注释早就写了"broadcastAll 就踩过这一下"，但代码一直没跟着改。
⇒ 4 处 `hint(` → `toast(`。

### 4. `Main.qml` — `Parameter "on" is not declared`（Qt 6 弃用写法）

```qml
onToggled: backend.notifyOnDone = on      // 旧式参数注入
```
`ToggleRow` 确实声明了 `signal toggled(bool on)`，**功能没坏**，但 Qt 6 已弃用注入语法。
⇒ 改成显式函数参数 `onToggled: function (on) { backend.notifyOnDone = on }`（2 处）。

### 5. `viewerbackend.cpp` — 收流页临时文件写不进（**RTC 整条路是挂的**）

```
FAIL 收流页写不进临时文件 …/Temp/stelarith-viewer-rtc.html（拒绝访问。）
```

固定文件名 ⇒ 上一个实例（或它残留的 Chromium 子进程）还握着同名文件时，
新实例一开就永久失败，`setRtcState("failed")` 直接返回。
**画面看着还能动只是因为 JPEG 兜底**（日志里 `0.5 fps` / `2.0 fps`），实时流根本没建起来。

⇒ 文件名带 **PID**（`stelarith-viewer-rtc-<pid>.html`），各实例各写各的；
真写不进去时先 `QFile::remove` 清掉同名残留再试一次。补 `#include <QCoreApplication>`。

## 四、日志里另外两个 FAIL（**没修**，说明原因）

### `FAIL 文件推送中断：file_push: 目标打不开（C:\Users\Administrator\AppData\Local/xingjikong/incoming/install-agent.ps1）`

推送目标是 `TEST1`，而 TEST1 就是**本机这台 Administrator 机器** ——
被控端要落盘的目录 `AppData\Local\xingjikong\incoming\` 没建出来（或没权限），
所以"目标打不开"。这是**被控端**侧的问题（应在写文件前 `mkpath` 建目录），不在管理端。
（顺带：路径里 `...\AppData\Local/xingjikong/incoming/...` 混用了 `\` 和 `/`，Windows 一般容忍，但不干净。）

### `RTC 收到新 offer，丢弃上一轮残留的 2 个候选`

这条是**正常**的：被控端每隔几秒重发一次 offer，管理端把上一轮没用完的 ICE 候选丢掉。
不是错误。（配合上面第 5 条看：它之所以反复重发，正是因为管理端这边 RTC 一直没建成。）

## 五、这一轮最值钱的两条教训

1. **注释会撒谎。** `broadcastAll` 底下那段注释准确描述了 bug（"就踩过这一下"），
   但代码从没改过 —— 写注释不等于修好了。日志里反复出现的 ReferenceError 最能暴露这种脱节。
2. **固定名的临时文件在"程序可能被反复重启/残留"的场景下必翻车。**
   凡是 `%TEMP%` 里的东西，一律带 PID（或随机后缀），并在写失败时先清残留再重试。
