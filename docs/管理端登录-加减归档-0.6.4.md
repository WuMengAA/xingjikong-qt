# 管理端「网站账号登录」加减归档（viewer 0.6.4）

> 用户一句话「管理端登录」。诊断后发现问题不是"登录没做"，而是**三处断链叠在一起**，
> 导致 0.6.3 发出去的包里点登录**必失败**。本文件是这一轮改动的全账。

---

## 一、根因（改之前）

| # | 断链 | 现场表现 |
|---|---|---|
| 1 | `src/oauthlogin.cpp` 硬要求 `STE_OAUTH_CLIENT_SECRET` 非空才肯起流程 | 账户胶囊顶一句「没配 OAuth 客户端密钥」，点登录立刻失败，根本走不到网络 |
| 2 | 站点地址没兜底，环境变量为空 | 账户胶囊「未配置站点地址（只走静态令牌）」，装机现场无从下手 |
| 3 | 绿色包里**没有** `viewer.env`、也没有启动脚本 | 双击 exe 出来环境全空；打包只按 `.dll/.exe/.pak/.dat` 后缀拷根层文件，无后缀的配置被静默跳过 |

**第 1 条是真自己坑自己**：`xingjikong_native` 是 loopback 原生客户端，站点
`src/lib/server/oauth-clients.ts` 第 59 行写明「按 RFC 8252，桌面 loopback 客户端**可以不做密钥**」；
`validateClient` 里 `PUBLIC_CLIENT_SECRET = "PUBLIC"` 分支要的正是「对方**明确不带** secret」。
所以"没配密钥"是**正常状态**，不是错误状态 —— 代码把它判成失败，用户只看到一句看不懂的错。

**顺带挖出的死文件**：`deploy/viewer.env` 原本是 .bat 语法，而 `启动管理端.cmd` 把所有值（含明文静态令牌）
硬编码在 cmd 里，**压根没读 viewer.env**。改之前那文件谁也没用。

## 五、追认（2026-10-06 22:0x）：上一节那条「必须改 .env」的结论是**错的**，此处更正

上一轮我判断「站点 `.env` 里 `OAUTH_DESKTOP_SECRET` 是空值 → `validateClient` 里
`if (!expected) return false` 恒拒 → 必须改成 `PUBLIC`」，并把这条挂成"等用户点单"。
**端到端验证证明这个判断是错的**，站点侧一行都没改就通了。

### 为什么 `.env` 那行不是解药

密钥的真源在 **SQLite 表 `oauth_clients`**，不是 `.env`：

| 优先级 | 来源 | 说明 |
|---|---|---|
| 1 | `rowToRecord()` 的 `r.secret`（**库值**） | 非空就直接返回，后面一律不看 |
| 2 | `rec.secret`（清单里显式写的） | BUILTIN 里已是哨兵 `PUBLIC` |
| 3 | `secretEnv` → `process.env["OAUTH_DESKTOP_SECRET"]` | 只在 1、2 都为空时才轮到 |

实查 `content/stelarith.db`：`xingjikong_native` 的 secret **已经是 `PUBLIC`**、enabled=1。
所以 `.env` 那行空值从头到尾就没参与过判定 —— 改它不会让事情变好，也不会变差，是**死配置**。

> 也踩到一个坑：`/oauth/authorize` 返回 200 **不能**证明客户端可用。同意页有自己的
> 四道闸（`inspect`：登记 → 未停用 → 回拨合法 → `hasSecret`），我拿它当过"客户端 OK"的证据，
> 但它跟 token 阶段用的 `validateClient` 是两套判定。

### 真正的断链：构建产物上了，进程没换

| 时间 | 事件 |
|---|---|
| 18:45:32 | 生产进程启动（PID 8220），读到的是**那一版** `build/`（无 `PUBLIC` 分支） |
| 21:37–21:39 | `oauth-clients.ts` 改完、重新构建，`build/` 里出现 `if (expected === "PUBLIC")` |
| 22:0x（本次） | 探测 `/oauth/token`（不带 secret）→ **401 invalid_client**；运行日志全是「拒绝：客户端校验不通过」 |

产物里有分支、库里 secret 也是 `PUBLIC`，却依旧 401 —— 唯一自洽的解释是进程还跑在 18:45 那份产物上：
旧代码按 `safeEqual(expected="PUBLIC", secret="")` → false → 401。**改代码不重启，等于没改。**

### 实际动作（站点侧零文件修改）

只做了一件事：**重启生产进程**（PID 8220 → launcher 自愈拉起，22:08:02）。
`stelarith-launcher.bat` 的自愈循环会自己 `goto :loop` 起来；计划任务 `StelarithServer`
另有 5 分钟 TimeTrigger 兜底。站点工作区一个文件都没动（别人 WIP 原样留在原地）。

### 端到端验证（PASS）

用脚本复刻 0.6.4 管理端对 `xingjikong_native` 的行为（loopback 公开客户端、**不带** `client_secret`），
完整跑通：

```
[1] GET  /oauth/authorize          200   四道闸（登记/停用/回拨/密钥）全过
[2] POST /oauth/authorize?/login   200   同意页内联登录（密码从站点 .env 读，不打印）
[3] GET  /oauth/authorize          200   同意页出现（authed）
[4] POST /oauth/authorize?/consent 204   Location=http://127.0.0.1:53999/oauth-callback
    → 授权码到手，长度 32，state 一致
[5] POST /oauth/token（不带 secret）200  access_token=Bearer scope=cims ttl=2592000s
RESULT: PASS
```

安全边界也复验了：带一个瞎写的 `client_secret=deadbeef` 仍 **401**（公开客户端要求"明确不带"，
不是"随便塞个东西"）。站点 `/` 与 `/console/` 重启后 200 正常。

**结论：管理端 0.6.4 已发布的那份包（`8e5c426`，125.3 MB）现在即可用**，
不需要重新出包、不需要抬 ota —— 服务端行为与客户端 0.6.4 的发出方式本来就一致。
