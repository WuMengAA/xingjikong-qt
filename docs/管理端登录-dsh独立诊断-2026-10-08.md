## 根因 A ｜登录窗口「卡死」没有收口：一次没接住回拨 ⇒ 永远停在登录中（表现为"点了没反应/登不进去"）

**位置**
- `oauthlogin.cpp:159-171`（`openAuthUrl` 成功即视为开始，无任何超时/失败回收）
- `oauthlogin.cpp:189-225`（`openEmbeddedWindow` 只要 `show()` 成功就 `return true`，从不验证页面是否真的加载出了授权页，更没有 `loadFinished` 判据）
- `oauthlogin.cpp:235-250`（回拨服务器把**第一条到达的连接**当回拨，不做路径预筛）
- `viewerbackend.cpp:540-543` / `viewerbackend.cpp:482-504`（`m_accountBusy=true` 后只能靠 `succeeded/failed` 落地）

**机制（两条互锁的链，任一条成立症状都一样）**

1. **回调根本没到本机**（内嵌 QWebEngine 的页面白屏 / 被企业策略或安全软件拦 / 授权页加载失败），那么 `onReadyRead` 永远不触发 → `m_busy` 永远 `true`、`m_accountBusy` 永远 `true`、`stopServer()` 永远不执行、socket 一直 LISTEN。界面是"正在登录网站账号…"，**一条错误日志都没有**，用户只能关窗（关窗那一刻才补发 failed，但很多人只是干等）。
2. **回拨到了，但第一条连接不是回拨**：`onNewConnection()`（:237-249）无条件把第一路连接记成 `m_sock`。若浏览器在导航前先发了 `GET /favicon.ico`（QtWebEngine 的 `defaultProfile` 是磁盘持久 profile，完全可能做 speculative fetch），`onReadyRead` 走到 `pathOk=false` 分支 → `stopServer()` + `m_busy=false`（:299-308）→ **回拨服务已被拆掉**，紧接着真正的 `GET /oauth-callback?code=…` 落在已关闭的 server 上 → 连接被拒/无响应 → 浏览器报"无法访问此网站"。这一条**正好是本次改动新引入的**（:275-282 的注释说 2026-10-07 才把这个分支写全，之前是 400 但至少把 `m_busy` 复位），所以"以前能用、最近不能登"的可能性很高。
3. 附带的陈旧状态：`begin()` 没有清 `m_pending`（`oauthlogin.h:104` 注释说"本次回拨收到的 HTTP 请求原文"，但 `begin()` 里没有任何 `m_pending.clear()`）。上一次失败/取消留下的残包会拼到这一次的请求头上（:260），使 `head` 解析出的请求行不是本次的 → 直接掉进同一个 400 分支。**必须"上一次刚失败、马上再点一次登录"才复现**。

- 日志里**完全没有**这两行 → 属于机制 1（回调没到）：应有而没有 `[oauth] 正在打开授权页（回拨 http://127.0.0.1:<port>/oauth-callback, state=xxxxxxxx…）`（:157）之后的任何 `[oauth]`；`[account]` 那行停在 `[account] 网站账号登录成功` 之前。

- 出现 400 分支后，`viewer-run.log` 里**再没有** `[oauth] 回拨接住，正在换网站令牌…`（:320），而界面提示是"授权回拨校验没过（地址不对或状态不匹配），请重新登录"。

## 根因 B ｜换令牌响应键判据过窄：站点若只回 `access_token` 就当场判失败

**位置**：`oauthlogin.cpp:363`（`obj.value("token").toString()`；:361-362 的注释写的是"两个都认"，代码只认了一个）；失败文案在 `:365`。

**机制**：`/oauth/token` 返回体里如果这一版站点只给 `access_token`（或把令牌放在别的键、或多个键但 `token` 恰好为空），客户端拿到的 `sessionToken` 是空串 → 走 `:364` 分支 → `m_busy=false`、关窗、`emit failed("换回来的响应里没有 token…")`。现象是"授权页点完同意、看着像成功，随后弹一句失败"，站点侧完全健康（这正是《已排除》第 25–27 行的探测结果：客户端校验通过、卡在业务分支）。这是最经典的客户端解析 bug，且**代价极低就能排除/固定**。

**可验证判据**
- 日志里出现 `[oauth] FAIL 换回来的响应里没有 token（站点改了 /oauth/token 的返回？）：<原始 JSON 前 512 字节>`（:366）——**那 512 字节原始 JSON 就是终局证据**，直接看键名是 `token` 还是 `access_token`。
- 界面提示恰好是"换回来的响应里没有 token…"。
- 反证：如果日志是 `[oauth] 换到网站会话令牌（有效期 …秒）`（:374）那就不是这条。

**建议改法**：`token` → 取不到再取 `access_token`（并顺手取 `expires_in`）：
```cpp

```
同时把 `status != 200` 分支的日志（:352）也保留（那条已经有 `raw.left(512)`，很好）。

## 根因 C ｜`loggedIn()` 不看票的有效期 ⇒ 30 天后"看着已登录、其实连不上"，登录入口语义混乱

**可验证判据**
- 日志里 `[account] 读到本机凭据：账号=… 接入票 N 个字符，到期 …`（:452）的"到期"时间**已经过去**，但界面账户行写的是"已登录：…"或"网站会话过期，正在重新取票…"。

**建议改法**：`loggedIn()` 改成 `return (!m_cloudTicket.isEmpty() && ticketUsable(0)) || !m_token.isEmpty();`（与 `refreshAccountText` 保持同一判据）；:614 的"有会话但票不可用"路径补一行 `setStatus`/`logf`，别静默；`ensureCloudTicket(false)` 静默失败时至少 `refreshAccountText()` 让文案落到"需要重新登录"而不是"正在重新取票"。

# 3. 『失败后可恢复性』缺陷（单独成节）

以下都读自代码，与"哪个是本次根因"无关，建议一并修：

1. **换票请求在飞时二次调用会把界面锁在"正在登录"** — `viewerbackend.cpp:607-609`：`if (m_sessionReply) return;` 在 `m_accountBusy = true`（:625）**之后**才可能生效吗？不，是提前 return，但调用方 `ensureCloudTicket` 的 `m_accountBusy=true` 已在更早的路径里被别的调用置上：具体表现是 `ensureCloudTicket(false)` 被 `onAccountTimer`（5 分钟一次）或 `start()` 重入时，第一句就 `return`，而 `m_accountBusy` 保持 `true` 且**不再有任何东西会把它复位**（复位只发生在 `onOAuthSucceeded` / `onOAuthFailed` / `onSessionTicketFinished`）→ 界面永久停在「正在登录网站账号…」（`refreshAccountText` :485），再点登录被 `loginWithSite()` 的 `if (m_accountBusy) return;`（:524）**静默**吃掉。建议：早退前先判/复位，且 `loginWithSite()` 早退时至少 `logf` 一行（现在一句日志都没有）。
2. **`OAuthLogin` 没有超时收口** — 回调永远不来时 `m_busy` 永真、`stopServer()` 永不执行、127.0.0.1 上的监听 socket 一直开着，界面无错误、无法重试。见根因 A 的改法。
3. **`m_pending` 跨次登录不清** — `oauthlogin.h:104` 是成员缓冲（:257-259 的注释专门修过 `static` 污染），但 `begin()`（:83-142）没有 `m_pending.clear()`，残留会污染本次请求行解析。见根因 A。
4. **回拨 socket 指针未在"失败时被抢占"的分支复位** — `oauthlogin.cpp:239-245` 的第二路连接处理；`m_sock` 在 400 分支（:301）与成功分支（:314）都复位了，但**第一个连接若非回拨，服务就被拆了**（同根因 A 机制 2）。
5. **`m_sessionReply` 只在 `finished` 里置空**（`viewerbackend.cpp:575`）：若 reply 因故不发 `finished`（Qt 在 error 时通常也会发，但 `QNetworkAccessManager` 被销毁/进程退出等边界不保证），`m_accountBusy` 与 `m_sessionReply` 会一起卡住，无超时兜底。建议加 `QTimer` 超时或 `destroyed` 连接兜底。
6. **`loggedIn()` 与 `refreshAccountText()` 判据不一致**（:322 vs :489）——两个"登录态读数"用了不同真源，是"界面显示已登录但连不上"的结构性来源（根因 C）。
7. **`m_accountText` 在成功路径上不会被清成"已登录"**：`onOAuthSucceeded`（:551-559）只改 `m_sessionToken` 与 `m_accountBusy`，不碰 `m_accountFatal/m_accountText`，靠随后的 `onSessionTicketFinished` → `refreshAccountText()` 收口；如果那张换票请求失败（:577-585），界面会正确显示失败——这条是好的。但若换票请求**根本没发出去**（:608 早退），就永远停在旧文案上。
