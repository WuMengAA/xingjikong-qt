# 加减归档 · 被控端启动缺 OpenSSL 运行库（2026-10-10）

> 触发：用户提供两张截图 + 「全量测试，不测重启，重点文件传输应用启动」。
> 截图内容：`stelarith-agent-qt.exe - 系统错误：由于找不到 libssl-3-x64.dll / libcrypto-3-x64.dll，
> 无法继续执行代码。重新安装程序可能会解决此问题。` —— **被控端根本起不来**。
> 范围：`Stelarith-xingjikong-qt` 的**打包链路**（`.nsi` + `make-hotfix.mjs`）。**未改任何 C++ 源码。**

---

## 0. 一句话
被控端/管理端**静态链**了 libdatachannel，它的 DTLS 走 PostgreSQL 17 自带的 OpenSSL ⇒
两个 exe 的导入表里都有 `libssl-3-x64.dll` / `libcrypto-3-x64.dll`；而这两个名字
**匹配不上安装器里的 `Qt6*.dll` 通配**、windeployqt 也不认识 ⇒ 装完启动即报「找不到」。
本轮把这两枚 DLL **显式点进 6 个打包产物**（安装器 ×2 / 热修包 ×2 / 绿色包 ×2）并逐个验证。

---

## 1. 根因链路（逐环有据）

| 环 | 证据 |
|---|---|
| CMake 链了 PG17 的 OpenSSL | `Stelarith-control-qt/CMakeLists.txt:157-158` 与 `Stelarith-viewer-qt/CMakeLists.txt:211-212`：`"C:/Program Files/PostgreSQL/17/lib/libssl.lib"` / `libcrypto.lib`（libdatachannel 静态链的 DTLS 依赖） |
| exe 因此**直接导入**这两个 DLL | 自写只读 PE 导入表解析（`.workbuddy/tmp/pe_imports.py`）：`stelarith-agent-qt.exe` 与 `viewer-qt.exe` 的导入表内均含 `libssl-3-x64.dll`、`libcrypto-3-x64.dll` |
| 但仓库里**一个都没有** | `find . -iname "libssl-3-x64.dll" -o -iname "libcrypto-3-x64.dll"` → **0 命中**；`build/` 里 20 个 DLL 全是 Qt |
| 装机包也**不含** | `installer.nsi:153` 原为 `File "build\Qt6*.dll"` —— 通配只吃 `Qt6*`；`make-installer.nsi:114` 同理 |
| ⇒ 装完必报 | Windows 加载器解析导入表失败 → 截图里的「系统错误」 |

**顺带核实**：`VCRUNTIME140.dll` / `MSVCP140.dll` 教室机本来就有（`Qt6Core.dll` 早已依赖），
所以本次新增的**只有**这两枚 OpenSSL DLL，没有连带引入新的 VC 运行库问题。

| 文件 | 改动 | 为什么 |

| `Stelarith-control-qt/make-hotfix.nsi` | 热修段增补同两枚（`hotfix-staging\libssl-3-x64.dll` / `libcrypto-3-x64.dll`） | **只换 exe、老机器没有 DLL ⇒ 热修完照样起不来**。热修必须带运行库 |
| `Stelarith-viewer-qt/scripts/make-installer.nsi` | 在 `File "..\build\Qt6*.dll"` 后增补同两枚 | 管理端同样链了 ldc_receiver，同样缺 |
| `scripts/make-hotfix.mjs` | 新增 `OPENSSL_DLLS` 常量 + `stageOpenSsl()`；**两端**暂存时都拷入；`VIEWER_MUST` 加入这两枚（zip 缺件即 fail）；日志与体积提示同步 | 热修打包器原本只 stage `exe`（被控端）/`exe+qml`（管理端），不带运行库；且管理端 zip 的"必需件"门槛要覆盖它们 |
| `Stelarith-viewer-qt/scripts/make-portable.mjs` | `REQUIRED` 增补两枚 OpenSSL | 绿色包靠 `.dll` 后缀拷 `build/`，本会带上，但清单不检查 ⇒ build/ 缺件静默 |
| `Stelarith-control-qt/scripts/make-portable-agent.mjs` | `REQUIRED` 增补两枚 + 新增 `FROM_BUILD_FILES`（从 `build/` 显式取） | **绿包 DLL 从 `deploy/` 拷，而 `deploy/` 根本没这两枚** ⇒ 永远带不上（详见 §7） |

**无删除。** 三个 `.nsi` 改后**BOM 仍在**（`efbbbf`）—— 已逐个复验，未触发 `Bad text encoding`。

## 5. 顺带发现（登记，未处置）

### 5.1 被控端版本号三处不一致（既有状态）
| 处 | 值 |
|---|---|
| `CMakeLists.txt` `AGENT_VERSION` | `0.6.24-rc.4` |
| `src/main.cpp` `kAppVersion` | `0.6.24-rc.4` |
| **`build/version.nsh`（安装器读它）** | **`0.6.24-rc.3`** |
| **`build/stelarith-agent-qt.exe`（内嵌）** | **`0.6.24-rc.3`** |

⇒ 源码 bump 到 rc.4 后**被控端没有重新 configure/编译**，`version.nsh` 与 exe 停在 rc.3。
直接后果：`make-hotfix.mjs` 按源码读 `rc.4` 去认产物、makensis 按 `version.nsh` 写成 `rc.3`
→ 脚本末检 `fail('makensis 没产出预期文件')`。**这是既有问题，非本轮引入。**
（管理端侧 `build/version.nsh` 与源码**一致**，都是 rc.4，无此问题。）

### 5.2 老问题复现（不用 taskkill）—— 无。本轮**未执行**任何 install/卸载。

## 6. 遗留待办（需归属方或用户决定）

1. **让 DLL 随构建自动就位（durable fix）**：现在这两枚是我**手工 cp 进 `build/`** 的；
   一旦 `build/` 被清空重建，它们就没了 → `makensis` 会因 `File` 找不到而**报错中止**（响亮失败，非静默），
   `make-hotfix.mjs` 也会带明确提示 fail。**根治**应在两端 CMakeLists 加一条 POST_BUILD 拷贝。
   ⚠️ `Stelarith-control-qt/CMakeLists.txt` 当前**有他人未提交改动**（`M`），**本轮未碰**。
2. **被控端重新 configure + 编译**，让 `version.nsh` / exe 与源码 rc.4 对齐（同样属他人在改的文件）。
3. **应用源**：OpenSSL 取自 `C:\Program Files\PostgreSQL\17\bin`（构建机依赖）。若要摆脱这个
   构建机耦合，应把两枚 DLL 收进 `_probe/ldc_libs/` 或 `third_party/openssl/` 并从那里取。

## 7. 补充（同日晚）：便携包（绿色包）出包路径 —— 首轮漏掉的第 4、5 条路

首轮只修了 **NSIS 安装器 + 热修包**，漏了**绿色包（portable zip）**。核查发现两种绿包脚本的
取件逻辑**不一样**，因而漏点也不同：

| 脚本 | 取 DLL 的方式 | 后果 |
|---|---|---|
| `Stelarith-viewer-qt/scripts/make-portable.mjs` | 从 `build/` 拷所有 `.dll`（按后缀） | 会带上；但 `REQUIRED` 未列 ⇒ 缺件**静默**（同 0.6.0 漏 icudtl.dat） |
| `Stelarith-control-qt/scripts/make-portable-agent.mjs` | `copyDir(DEPLOY,…)` 从 **`deploy/`** 拷 | **`deploy/` 素材库没有这两枚 ⇒ 永远带不上** |

**实锤**：`dist/` 里已有 3 个绿包（agent-rc.1 / viewer-rc.1 / viewer-rc.3），7z 列包搜
`libssl-3-x64\|libcrypto-3-x64` **命中 0**；两端 `deploy/` 同样 0 命中。⇒ 这些绿包在干净机器上**都跑不起来**。

**修法**：
- 两端 `REQUIRED` 各增补两枚（缺件在出包自检当场炸，不再静默）。
- 被控端新增 `FROM_BUILD_FILES = ["libssl-3-x64.dll","libcrypto-3-x64.dll"]`，从 `build/` 显式取。

**实测（真出包 + 脚本自带 db 自检通过）**：

| 产物 | 大小 | 自检 |
|---|---|---|
| `Stelarith-viewer-qt/dist/stelarith-viewer-portable-0.6.24-rc.4.zip` | 134,655,827 B (128.4 MB) | 必需件 **20/20 齐** ✓；7z 确认内含 `libssl-3-x64.dll` + `libcrypto-3-x64.dll` |
| `Stelarith-control-qt/dist/stelarith-agent-portable-0.6.24-rc.4.zip` | 131,700,932 B (125.6 MB) | 必需件 **31/31 齐** ✓；日志 `+ libssl-3-x64.dll（来自 build/，deploy/ 没有）` |

⚠️ **两条必读提示**：
1. **管理端绿包名实一致**（包名与 exe 都 rc.4）⇒ 可直接用。
2. **被控端绿包名实不符**：包名读源码 `kAppVersion`＝`rc.4`，但其内 `stelarith-agent-qt.exe` 仍是 `rc.3`
   （§5.1 的既有不一致所致）⇒ **被控端重编到 rc.4 后应重出此包再发布**。
3. 这两个新绿包是**本轮验证的产物**，7z 实测含 OpenSSL；**未发布、未上 ota.json**。
