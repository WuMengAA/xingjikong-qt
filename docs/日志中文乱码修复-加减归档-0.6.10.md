# 0.6.10 加减归档 · 日志中文乱码

## 现象

真机日志里的中文全是这种：

```
[viewer] viewer-qt 鐗堟湰 0.6.9锛堟棩蹇楋細D:/…/viewer-run.log锛?
[viewer] 宸蹭粠 viewer.env 璇诲叆 3 椤归厤缃?
```

## 成因（实测，不是猜）

把那份日志的字节分别按两种编码解码：

| 解码方式 | 结果 |
|---|---|
| **GBK**（Windows 命令行代码页 936 / 记事本的默认） | `viewer-qt 鐗堟湰 0.6.9锛堟棩蹇楋細` ← **用户看到的就是这个** |
| **UTF-8**（文件真实内容） | `viewer-qt 版本 0.6.9（日志：` ← 其实一直是对的 |

原始字节 `=== viewer-qt \xe5\x90\xaf\xe5\x8a\xa8\xef\xbc\x8c\xe6\x97\xa5\xe5\xbf\x97=…`
（`\xe5\x90\xaf\xe5\x8a\xa8` = "启动" 的 UTF-8）。

⇒ **日志写的是 UTF-8，查看端按 GBK 解，于是每个汉字都变成两个莫名其妙的字。**
"鐗堟湰" 就是"版本"的 UTF-8 字节被当 GBK 读出来的样子。

## 改法：出口统一转本机编码

内部一律 `QString`（Unicode），**写盘 + stdout 一律 `toLocal8Bit()`**（GBK）。

### 修改 `src/main.cpp`
- 新增 `writeLogBytes(const QByteArray &)`：按字节原样写盘（出口 primitives）。
- `writeLog(const char *s)`：入参约定 UTF-8，`QString::fromUtf8(s).toLocal8Bit()` 后写盘；
  初始化时的两行提示（"日志写不进" / "=== viewer-qt 启动"）也改走 `QStringLiteral(...).toLocal8Bit()`。
- `logf()`：`vsnprintf` 出来的 UTF-8 先转本机编码，**写盘和 stdout 用同一份**（以前 stdout 直接打 UTF-8，
  控制台同样是乱码）。
- `installMessageHandler()`：不再手拼 UTF-8 的 `char line[2048]`，直接
  `QStringLiteral("[viewer] %1: %2").arg(QLatin1String(tag), msg).toLocal8Bit()`，
  stdout 与写盘共用。

### 修改日志参数的编码（统一成 UTF-8 入参）
- `src/main.cpp`：启动行 `logFilePath().toLocal8Bit()` → `toUtf8()`
- `src/viewerbackend.cpp`：2 处日志参数 → `toUtf8()`
- `src/oauthlogin.cpp`：12 处日志参数 → `toUtf8()`

⚠️ **刻意保留 `toLocal8Bit()` 的两处**：
- `writeLog()` 里 `fopen` 的路径（**路径必须本机编码**，UTF-8 的 fopen 打不开中文目录）；
- `viewerbackend.cpp` 的 `accountFilePath()`（同样是路径）。

### 版本
`0.6.9 → 0.6.10`（`CMakeLists.txt` + `src/main.cpp`）。

## 验证

- 编译 `build-qt-viewer.bat` → `[exit] 0`
- 出包 131,447,173 B / 条目 1394 / 必需件 18/18 / sha256 `3c9a4b20…`
- ota 已指向 0.6.10
- **乱码成因有实测证据**（上表双解码对比）

⚠️ **没做离屏自检**：用户机器上正开着 `pkg-0.6.9`（PID 18400），单实例互斥体会把自检实例挡掉，
没有擅自关它。也就是说"新版日志在命令行里确实是中文"这一步**要等装上 0.6.10 后由用户确认**。

## 取舍（说清楚）

写 GBK 之后：
- ✅ 命令行 `type viewer-run.log`、记事本、Everything 预览 → 中文正常
- ❌ 用 UTF-8 编辑器（VSCode 默认）打开 → 会乱

反过来写 UTF-8 则完全相反。选 GBK 是因为看日志的人是老师/运维，用的是命令行和记事本。
真要用 UTF-8 工具看，可以在命令行里 `chcp 65001` 之前先别改回来 —— 这个取舍已写进代码注释。

## 顺带记一条通用教训

**Windows 上"写日志"这件事，编码必须在出口定死，不能让调用方各写各的。**
原来就是 `logf` 的格式串是 UTF-8、参数有的 `toLocal8Bit` 有的不是 —— 半对半错，
所以才会出现"文件本身没坏、但谁看都是乱码"这种最难查的情况。
