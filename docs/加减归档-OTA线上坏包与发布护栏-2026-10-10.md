# 加减归档 · OTA 线上坏包 + 发布护栏（2026-10-10）

> 触发：排查"被控端启动缺 OpenSSL"（另见 `加减归档-被控端启动缺OpenSSL-2026-10-10.md`）时，
> 顺手核对 `ota.json` 发布状态，发现 **正在对外分发的两个包本身就是坏的**。
> 范围：`Stelarith-cloud-ws/scripts/publish-release.mjs`（发布链路）。**未改任何包内容、未发布。**

## 0. 一句话
`ota.json` 当前发布的两个包（agent / viewer 各一）**缺 `libssl-3-x64.dll` / `libcrypto-3-x64.dll`** ——
就是用户截图里那个「系统错误」。而发布脚本的 `check` 只核对「清单 vs 磁盘文件」，
**从不看包内有什么**，于是这个坏包被它评为「一致 ✓」，一路发到了教室机。

**处置**：① 加发布前包内容自检（§4，commit `87d08c9`）；② **已重发修好的包止血**（§6，2026-10-10 11:15）。

## 2. 性质与影响面
- 这是**正在发生的**生产问题，不是隐患：官网装机卡与 OTA 指向的都是这两个包。
- **新装机 / 手动重装 / 升级**都会拿到缺 DLL 的包 → 双击即报错、根本起不来。
- **存量设备不受升级波及**：版本号仍是 rc.3，与云端相同 ⇒ OTA 不触发（不会"升级"到自己）。
  ⇒ 风险集中在"**新装机**"这条路上。

---

## 3. 根因（两层）
1. **打包层漏件**（已另档修复）：`.nsi` 的 `File "build\Qt6*.dll"` 通配吃不到 `libssl*`，
   green 包脚本 `deploy/` 路径也没有 —— 见 `加减归档-被控端启动缺OpenSSL-2026-10-10.md`。
2. **发布层无内容校验**（本档修复）：`publish-release.mjs check` 只验证
   "清单描述的 = 磁盘上这个文件"（存在性 / size / sha256），**不验证"这个文件装上去能用"**。
   ⇒ 包缺件时，校验全过。

---

## 4. 修复（`publish-release.mjs`，commit `87d08c9`）
| 新增 | 作用 |
|---|---|
| `REQUIRED_ENTRIES` | 每个产品的必需运行时件：agent=`stelarith-agent-qt.exe`+两枚 OpenSSL；viewer=`viewer-qt.exe`+`qml/Stelarith/Main.qml`+两枚 OpenSSL |
| `listArchiveEntries(file)` | 用 `7z l -slt` 解包列条目（NSIS exe 与 zip 通吃），正斜杠归一化 |
| `verifyPackageContent(product,file)` | 返回 `{ok, missing, error}`；缺件/读不了都在此暴露 |

接线：
- `publish`：算完 sha256 后、**落盘前**自检 —— 缺件 `fail()`，**宁可发不出去**。
- `check`：文件与清单一致时**继续校验包内容** —— 缺件同样计入 `bad`（退出码 1）。

⚠️ **实现坑（实测锤定）**：解析必须用 `-slt`（逐条目 `Path = …`）。
`-ba` 的固定列正则在 **NSIS** 上会失效 —— NSIS 输出列是 `date time attr size name`（**无 compressed**），
zip 是 `… size compressed name`；沿用 zip 的正则会丢光所有行 ⇒ 全判"缺件"（第一版就踩了）。

## 6. 止血：重发修好的包（**已执行** 2026-10-10 11:15）

用户授权「自行推进」后已重发。**策略：两端都保 `rc.3` 版本号、只替换坏内容** ——
不构成版本推进（不触碰"发不发 rc.4"这个被挂起的决定），且**对存量设备零波及**。
（补一个反直觉的点：**被控端崩了根本跑不了 OTA** ⇒ "升版本自动修复存量"这条本来就不成立，
只能手动重装；重装走的也是同一个 URL，所以保版本号换内容已经能修好所有可走通的路径。）

| 产品 | 修复件来源 | 做法 | 结果 |
|---|---|---|---|
| agent | `control-qt/dist/stelarith-agent-setup.exe`（含 OpenSSL 的 rc.3 内容包） | 复制 → `dist/republish/stelarith-agent-setup-0.6.24-rc.3.exe` | size `94626768`，sha `d5911e0b…` |
| viewer | 原 rc.3 绿包（唯一缺陷就是缺两枚 DLL） | 复制 → `dist/republish/…rc.3.zip` 后**注入两枚 DLL** | size `133931572`，sha `5138e5e3…` |

> **管理端为什么用"注入"而不是重出**：viewer 的 `build/` 已被 rc.4 构建覆盖，
> **无法再产出干净的 rc.3 绿包**；而 rc.3 包唯一缺陷就是缺这两枚 DLL
> ⇒ 补上即回到"rc.3 本应有的样子"，不外推版本、不触发存量升级。

命令（实际执行，`--notes` 已更新为含修复说明）：
```bash
cd Stelarith-cloud-ws
node scripts/publish-release.mjs publish --product agent  --version 0.6.24-rc.3 \
  --file ../Stelarith-control-qt/dist/republish/stelarith-agent-setup-0.6.24-rc.3.exe --notes "…"
node scripts/publish-release.mjs publish --product viewer --version 0.6.24-rc.3 \
  --file ../Stelarith-viewer-qt/dist/republish/stelarith-viewer-portable-0.6.24-rc.3.zip --notes "…"
```
