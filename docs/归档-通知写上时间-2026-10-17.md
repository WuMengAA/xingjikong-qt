## 一、为什么这是「修 bug」而不是「加装饰」

用户说「时间逻辑也改改」，我先取证，发现两个**真 bug**，都在上一轮埋下（上一轮把时间文本
固化进 JSON 是我自己做的决策，本轮推翻）：

### Bug 1：`ts` 记的是**归档时刻**，不是发生时刻

`archiveToHistory()` 原文：

```cpp
h.ts = QDateTime::currentSecsSinceEpoch();   // ← 归档那一刻
```

而归档**不在通知出现时发生**，在「被下一条顶掉」或「收回空闲」时发生（`showIsland` 开头、
`enterIdle` 里各一处）。后果：

| 场景 | 实际 | 旧逻辑记成 |
|---|---|---|
| 10:00 弹出，10:30 被下一条顶掉 | 10:00 | **10:30**（晚半小时） |
| 23:59 弹出，00:03 被顶掉 | 23:59（昨天） | 00:03（**第二天**，「今天」组） |
| 长驻通知（带按钮、等点击）2 小时 | 起点 | **终点** |

设计稿 `docs/目标/灵动岛通用简单历史通知 — 设计.md` 字段表明确写：`ts` = **发生时间**。
所以这是实现偏离设计，不是口味问题。

### Bug 2：`dateGroup` / `timeStr` 是**归档时算好的死值**

上一轮为了让 QML「不现算日期」，把两者写进 JSON 并原样读回显示。后果是跨天后永久错：

- 昨天 20:00 归档时算出的 `dateGroup = "今天"` —— **今天打开仍显示「今天」**（7 天保留期内必现）；
- 昨天归档的 `timeStr = "23:50"`（当时按"今天"格式化，没日期前缀）—— 今天看还是 "23:50"，
  与分组标题「昨天」拼起来信息是残缺的。

而且这两件事叠加：分组写错 + 时间串写错，用户看到的是"这条通知时间完全不对"。

## 三、时间文本口径（迁移对照表）

| 用途 | 函数 | 输出 | 为什么 |
|---|---|---|---|
| 岛上正在显示的那条 | `noticeTimeOf` | `14:05`；跨天补 `10/16 14:05` | 形态最窄 320px，塞日期会更挤；跨天几乎不发生，但真跨了不能显示错 |
| 概览面历史面板 | `historyTimeOf` | `14:05` | 该列表有「今天/昨天/10月14日」**分组标题**，行内再写日期是冗余（"昨天 昨天 10:23"） |
| 历史面 face 2 | `historyTimeFullOf` | `14:05` / `昨天 14:05` / `10/14 14:05` | 该面是**平铺列表、没有分组标题**，日期必须自带 |
| 分组标题 | `historyDateGroupOf` | `今天` / `昨天` / `10月14日` / `2025年10月14日` | 按当前日期现算，绝不持久化 |

**旧 → 新对照（会影响已有数据）**

| 项 | 旧行为 | 新行为 |
|---|---|---|
| `HistoryItem::ts` 语义 | 归档时刻 | **发生时刻** |
| `HistoryItem::timeStr` 语义 | `HH:mm` / `昨天 HH:mm` / `M/d HH:mm` 三档混用 | 统一 `HH:mm`（仅落盘留档，显示不用） |
| `dateGroup` | 归档时算，落盘后不再变 | 每次组装按 ts 现算 |
| 存量 41 条老数据 | 分组可能已错（跨天） | **自动纠正**（下次打开就按真实 ts 显示） |
| 新增 QML 字段 | — | `history[i].timeFull` |

> 兼容性：`timeStr`/`dateGroup` 仍在 JSON 里写（调试与回滚用）。老数据无需迁移脚本 ——
> 显示层已完全不读它们。

## 四、验证证据（可复现）

编译：`scripts/_build_agent.py` → 链接通过，`[island-parity] OK 16 件`、`[ui-parity] OK 20 件`。

### 证据 1：五种形态时间就位（离屏探针截图）

| 命令 | 几何 | errors | 截图结论 |
|---|---|---|---|
| `--expand` | 332×320 | 0 | 标题右侧 `14:13`；历史面板「今天 / 09:53」 |
| （默认收起） | 332×56 | 0 | 标题右侧 `14:14` |
| `--form banner` | 752×72 | 0 | 最右端 `14:14`，描述不撞时间 |
| `--form centered` | 320×200 | 0 | 右上角 `14:15` |
| `--form fullscreen` | 752×752 | 0 | 右上角 `14:15`（与描述同字号） |
| `--form mini` | 112×112 | 0 | 无时间（设计如此），版式未受影响 |

### 证据 2：死值被现算覆盖（负向构造）

往探针历史文件写 3 条，`dateGroup` 与 `timeStr` **故意写成错误值**：

| 构造 ts | 写入的 dateGroup / timeStr | 实际显示 |
|---|---|---|
| 今天 09:05 | `昨天` / `假时间C` | **今天 / 09:05** |
| 昨天 09:00 | `今天` / `假时间A` | **昨天 / 09:00** |
| 前天 21:00 | `今天` / `假时间B` | **10月14日 / 21:00** |

⇒ 三个日期分支都按真实 ts 重算，存死的错误值被完全忽略。

face 2（`timeFull`）：`时间验证 1 → 09:05`、`前天那条 → 10/14 21:00` —— 平铺列表带日期前缀。

### 证据 3：`ts` 取的是出现时刻（决定性）

命令：`_island_qml_probe.py --form centered --actions --hold 5`
（第一条 `showIsland` → 停 5 秒 → 第二条顶掉 → 归档）

```
文件写入时刻 = 14:21:12
  课件已下发   ts=14:21:07  ⇒ 比归档写入早 5.2 秒
```

旧逻辑会得到 `ts = 14:21:12`。**5.2 秒的差值就是"出现"与"归档"之间的停留时间。**

### 证据 4：门禁

`node Stelarith-shared-qml/scripts/test-island-forms.mjs` → **21 通过 / 0 失败**。

## 五、本次我自己抓到的两个错（记账）

1. **Banner 里读了 `bTime.implicitWidth`** —— 写的时候觉得"bTime 没有 elide，应该没事"，
   但 `test-island-forms` 的规则拦下了（`面组件的 width 绑定不读 implicitWidth`）。
   规则是对的：只要哪天给 bTime 加上 elide 就会成环，而且真机上这类环是**每秒刷屏**的。
   改法：加 `TextMetrics { id: tmTime; font: bTime.font; text: bannerFace.time }`，
   用 `tmTime.advanceWidth`。
2. **胶囊时间是 10px + `rightMargin: 42`** —— 首版截图里时间与右下鲸鱼糊在一起，读不清。
   改 11px + 46。这类"看着能过、实际挤"的问题只有截图能发现，qmllint 不会报。

| **历史条目的时间刷新时机** | ⚠️ 有边界 | `history()` 在 `changed` 时重算。若通知列表长时间不触发 `changed`，跨零点后分组不会自动刷新（要等下一次 `sync()`）。实际影响小（打开面板/新通知都会触发），但不是零 |
