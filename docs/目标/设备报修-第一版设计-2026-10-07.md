# 星集控 · 设备报修（第一版设计，2026-10-07）

> 对应《全量设计文档》10.3「设备报修（中）」。某台教室机坏了，老师/管理员
> 报修并跟踪处理进度——补上「从报修到修复」的闭环。

## 一、场景与目标

| 角色 | 动作 | 期望 |
|---|---|---|
| 老师 | 课上发现教室机坏了 → 报修 | 30 秒内提交，不用找 IT |
| IT/管理员 | 看到报修列表 → 处理 | 知道哪台、什么症状、多久前报的 |
| 学生 | 无感 | 不参与 |

**验收**：老师点「报修」→ 填症状 → 提交；管理员在后台/管理端看到报修卡片
（设备 uid + 症状 + 时间），标「处理中 / 已修复」；被控端修好后自动恢复正常。

## 二、数据模型

```
RepairTicket {
  id: string            // tick-20261007-001（单调）
  uid: string           // 设备 uid（哪台坏了）
  reporter: string      // 报修人（老师账号）
  symptom: string       // 症状描述（一句话，≤ 200 字）
  severity: low|normal|urgent
  status: open|processing|fixed|closed
  at: ISO 时间          // 报修时间
  note: string?         // 管理员备注
  closedAt: ISO?        // 关闭时间
}
```

第一版存储：**云端内存表 + 备份随 backup.mjs 落盘**（简单；量小，每日备份足够）。

## 三、接口设计

| 接口 | 方法 | 权限 | 说明 |
|---|---|---|---|
| `/api/repairs` | GET | 管理端令牌 | 报修列表（可按状态过滤） |
| `/api/repairs` | POST | 老师/管理端令牌 | 新建报修 `{uid, symptom, severity}` |
| `/api/repairs/{id}` | PATCH | 管理端 | `{status, note}` 更新（处理中/已修复） |
| `/api/repairs/{id}` | DELETE | 管理端 | 关闭/删除 |

**管理端 WS**：报修列表随 `instruction-result` 无关——用 REST 拉取 + 手动刷新
（第一版不做推送；数量少，刷新即最新）。

## 四、管理端 UI（第一版）

集控页新增「设备报修」卡片：
- 「报修」按钮：弹小表单（选中设备预填 uid + 症状输入 + 严重度三选）→ POST。
- 列表：报修卡片（uid / 症状 / 时间 / 状态徽标），点卡片操作（处理中/已修复）。

## 五、被控端（第一版不动）

被控端**不主动上报故障**（第一版：坏了就黑屏/离线，靠老师报修）。
后续增强：被控端检测到连续 3 次注册失败 / 磁盘满 → 自动发一条 `repair.suggest`
事件（WARN 级别，管理端提示"疑似故障，可一键报修"）。

## 六、复用的现成机制

- **令牌**：管理端/老师 REST 用现有 viewer 令牌或站点票据（同 `/api/recordings`）。
- **审计**：报修创建/处理都进 `events.log`（`pushEvent`）。
- **备份**：`backup.mjs` 增加 `repairs.json` 备份项。

## 七、边界与安全

- 报修仅资源类操作（不执行），**不影响设备控制权限**。
- 报修列表只对**有权限看设备**的人开放（同设备表权限）。
- 不泄露：症状是老师填的话，不强制脱敏（内部系统）。

## 八、开发顺序

1. 云端 `/api/repairs` CRUD（内存 + 备库）→ 可单测
2. 管理端集控页报修卡片（表单 + 列表）
3. 被控端自动建议报修（后置）
