# 星集控 · 数据统计报表（第一版设计，2026-10-07）

> 对应《全量设计文档》10.3「数据统计报表（低）」。基于**已有的审计事件流水**
> （events.log）做统计，不新增数据采集——先证明「事件流水能出报表」再谈扩展。

## 一、目标与范围

| 维度 | 第一版 | 不做（后置） |
|---|---|---|
| 设备在线率 | 每日/每周在线时长占比 | 分钟级粒度 |
| 指令量 | 按动作统计（锁屏/关机/通知/广播…） | 按人按设备的详细报表 |
| 告警数 | 每日 error/warn 计数 | 告警分类趋势 |
| 广播量 | 广播条数/覆盖设备数 | 送达率漏斗 |
| 报表形式 | 管理端 REST JSON + 简单表格页 | 图表（echarts 集成后置） |

**验收**：`GET /api/stats?days=7` 返回近 7 天每日统计（在线率/指令量/告警），
管理端「设置」页加一个只读统计卡片能看。

## 二、数据源（纯现有，不新增采集）

| 指标 | 来源 |
|---|---|
| 设备在线状态采样 | `registry.js` 的 `touchHeartbeat`（每设备每次心跳更新时间戳）→ 统计时按「最后心跳在窗口内」判在线 |
| 指令量 | `events.log` 的 `设备真实执行回执 action=xxx`（recordResult 记） |
| 告警 | `events.log` 的 level=error/warn 行 |
| 广播量 | `events.log` 的「语音帧/广播帧已推给被控端」info |

**实现**：内存累计 + 按日滚动；重启丢失（第一版接受——报表是趋势不是对账）。

## 三、接口

```
GET /api/stats?days=7          → { ok, days: [{date, onlineRate, instructions,
                                             alerts, broadcasts}] }
GET /api/stats/summary         → { ok, devicesOnline, devicesTotal,
                                    instructionsToday, alertsToday }
```

- 权限：管理端令牌（同 `/api/devices`）。
- `summary` 给管理端顶部/概览页一行字；`days` 给报表表格页。

## 四、管理端 UI（第一版）

设置页（或概览页底部）加「运行统计」卡片：
- 一行：`N 台在线 / M 台 · 今日指令 X · 今日告警 Y`
- 展开：近 7 天表格（日期 | 在线率 | 指令 | 告警）。

## 五、实现要点

- `registry.js` 新增 `stats.js` 或并入 registry：`recordStat('instruction')` 等轻量计数器
  （每事件 +1，按日期 key），`getStats(days)` 汇总。
- **不改现有事件路径**：只在 `pushEvent` / `recordResult` 里顺手 `recordStat`（几行，
  不加新依赖）。
- 在线率：统计时遍历设备表，`lastSeen` 距今 < 10 分钟（= 心跳超时阈值）判在线。
  每天采样一次（0 点），存当日值。

## 六、安全与隐私

- 报表是**聚合**数据（不暴露单台设备细节到报表接口之外的维度）。
- 权限同设备表；不泄露学生信息（无姓名/班级维度的个人数据）。
