### dsh 抓出的严重问题（已修）
1. **`m_fadeAnim` 的 `finished→hide` 连接只增不减**：淡入淡出共用同一条动画，`finished` 两边都发，
   而两处 connect 的 lambda 都是无条件 `hide()`，且**从不解绑** ⇒ `STE_QT_ISLAND_IDLE=0` 下
   **第一条之后每条提示只闪 220ms**。而且 `Qt::UniqueConnection` **对 lambda 不生效**（只打告警照样连）。
   → 改成成员槽 `onFadeFinished()` + `m_closing` 状态位：只有"这次是淡出"才 hide。
2. **`m_dismissGuard` 没被 `showIsland()` 取消** ⇒ 旧守卫到点把新提示打掉。→ `showIsland()` 开头 stop。
3. **交互态展开永不回收**：`m_autoClose` 的 `if (m_interactive && m_expanded) return;` 一返回就不再排期，
   而空闲/文件提示的岛都是 interactive ⇒ 点开就永远压在屏幕顶部吃点击。
   → 新增 `m_expandGuard`（20s 硬超时，`kExpandMaxMs`）。
4. **`hitOpenButton()` 上下各 +8px 是假的**：鼠标局部坐标必在 `rect()` 内，`top()-8`/`height()+16`
   那两块永远收不到事件。→ 去掉负偏移，改横向 `kOpenBtnW 44→64`。
5. **手势用局部坐标**：拖拽时窗口自己位移（空闲 y=10 → 展开 y=24）会污染 `dy`。
   → 改 `ev->globalPosition()` 存全局起点 + `m_pressed` 布尔（`QPoint()` 的 (0,0) 是合法按下点，不能当哨兵）
   + release 校验 `Qt::LeftButton`。
6. 其他：`enterIdle()` 改状态不 `emit expandedChanged` / `setIdleEnabled(false)` 残留 `m_interactive=true` /
   `ensureIdle()` 判据应为 `isVisible()`（原判据会把正在显示的内容顶掉）/ 删掉只有声明无定义的
   `applyTheme()`、`positionForCurrent()` / `openInShell()` 补失败日志。

## 二、管理端「无法登录」排查 + 两端出包

### 排查方法（先实测再下结论）
对线上站点做了**只读 HTTP 探测**（python urllib），结果：
| 探测 | 结果 | 结论 |
|---|---|---|
| POST /oauth/token 不带 client_secret | 400 `invalid_grant` | 客户端校验**通过** ⇒ 公开客户端，不带密钥是对的 |
| 带乱填 client_secret | 401 `invalid_client` | 站点走 PUBLIC 分支：**必须不带** |
| GET /oauth/authorize（参数齐全） | 200「授权登录」 | 授权页与回拨地址规则正常 |
| POST /api/console/desktop/session 无 token | 401 | 换票端点存在且鉴权正常 |
⇒ **服务端整条链路健康**，我最初"密钥不对"的假设被自己的探测证伪（没猜，测了）。

### 客户端已修（真缺陷）
1. **登录总超时收口**（`kLoginTimeoutMs = 3min`）：原来回拨不来就 `m_busy` 永真、端口不关、
   界面永远"正在登录…"，再点只会命中"上一次还没走完" ⇒ **"点了没反应"**。stopServer() 里统一停超时器。
2. `begin()` 开局清 `m_pending`（跨次登录的回拨残留会污染请求行解析）。
3. 换令牌响应**兼容 `access_token`**（原来只认 `token`，站点若回归标准 OAuth2 就当场判失败）。
4. **站点错误正文人话化** `humanizeSiteError()`：SvelteKit 回的是整张 HTML 错误页，原因在 `<title>` 里
   （如「该账号没有查看集控的权限」），原来把 256 字节 HTML 原样贴给用户 ⇒"登录失败但不知道为什么"。
   另按 401/403/500 各补一句"接下来该做什么"。
5. `loggedIn()` 改看票时效（原来只看非空）⇒ 票过期后不再假显示"已登录"。

### 关键旁证：QML 双源分叉

## 三、管理端五连修（退出登录/面板出屏/切设备/离线/OTA）

### ⚠️ 最大教训：Popup 的**父层**才是坐标系的本体（别再修算法）
用户报「用户面板的界面不在屏幕内」+「无法退出登录」——**同一件事**。
- 前两次修都在改算法/加边界夹取，全错。真根因：`Popup` 没挂到浮层上。
  探针实测：**`parent=AccountMenu_QMLTYPE_63`、`Overlay.overlay === null`**
  ⇒ x/y 被解释成"相对顶栏那一格（150x28）"的偏移 ⇒ 菜单被摆到窗口右边 1900px 外，
  **一个像素都没画出来**，而 `menu.visible/opened` 全是 true、日志一片正常。
- 修：`Popup { parent: hostLayer }`（hostLayer = Main.qml 的 acctLayer，铺满窗口、z=9990）
  + `place()` **每次打开现算**落点（绑定会缓存第一次求值，而 Overlay.overlay 在弹窗打开前是 null）。
- 取证：**PrintWindow 拍不到 Popup 那一层**（主窗清爽、菜单在不在都拍不到）⇒
  必须 `BitBlt from 屏幕 DC`（新增 `scripts/_shot_screen.py`）；且抓屏进程必须
  `SetProcessDpiAwarenessContext(-3)`，否则整块图偏移（实测偏 140x60 = 1.5 倍缩放差）。
- 结论证据：`shots/_shotcheck/p21-final-screen.png` 里能看到菜单本体和「退出登录（清掉本机凭据）」。
- 顺带：`刷新 accountText 时"文案没变就不发信号"`是"登不出去"的第二半 ——
  accountChanged 还驱动 loggedIn/菜单显示哪一组，文案没变不等于状态没变 ⇒ 改成无条件发。

### 切设备只显示第一台（根因是**订阅没退**）
云端 `subscribeViewer` 只 `v.subs.add()`、从不替我们取消；被控端是"有人看才抓屏发帧"
⇒ 切设备后旧设备一直发帧，两台都写同一个 `m_frame`。修：
① `setCurrentUid` 先 `unsubscribe` 上一台；② `applyFrameBytes` **按 uid 分诊**
（非当前非缩略图直接丢；缩略图帧只进缩略图槽、不碰主画面）。
③ 新增 `frameUid` 属性 + QML `frameReady = frameUid === currentUid`，
   切换瞬间旧画面作废、显示"正在接入这台机器"（老师照着旧画面操作新机器＝事故）。

### 离线显示（补"设备台账"）
云端 `listDevices()` 只列当前连着的、`online` 写死 true，掉线即消失；而界面早就按台账写好了
（离线筛选/状态点/offlineDevices/批量离线直判失败）。⇒ 管理端侧自己记台账：
uid→最后见到的设备对象，消失即 online=false + lastSeenAgoSec，24h 过期、上限 200；
新增 `onlineCount` 给顶栏/概览/左栏计数（原来用 devices.length，含离线会虚高）。
⚠️ 台账是**进程内内存态**，重启从空重建（没做持久化——不需要）。

### 窗口在小屏放不下（防御性）
1280x720 那类教室屏：默认 760 高 / 最小 680 高 + 标题栏 + 任务栏 ⇒ 底栏必被切。
修：右栏动作区改**可滚动 Flickable**（代码里原本就写着"下次该改可滚动"）、默认 700/最小 600、
main.cpp 新增 `fitWindowToScreen()`（**先放宽最小尺寸再夹尺寸和位置**，否则 setGeometry 被
minimumSize 顶回去；在 load 后 / 首帧 frameSwapped / 700ms / 托盘唤回 共四处调用）。
⚠️ **只夹一次不够**：`engine.load()` 返回时 Qt 还没把 QML 请求的尺寸应用到窗口（日志实测一次都没触发）。
⚠️ 用户在我取证期间把显示改成 2560x1440（Qt 逻辑区 1707x960），当前窗口已装得下 ⇒
    "底部被切"本机此刻不再复现，属于防御性修复。

### OTA：不是坏文件，是**新包没发布**
`ota.json` 里 agent=v0.6.22（指向 650KB 裸 exe）、viewer=v0.6.14，而两端构建都是 0.6.23-rc.1；

`lastError="url 不合法"`（main.cpp:2357 的护栏，曾收到过无 url 的升级通知），当前 ok。

## 四、WebRTC 推流诊断（只读，未改一行）

### 链路现状（三层都已实现）
- **被控端推流**：`control-qt/main.cpp:3723 kRtcPage`（内嵌 QWebEngineView 跑
  `canvas.captureStream(15)`，`__startStream/__signal/__tickRetry/__forceReoffer/__diag`）。
  每 200ms `rtcTickOnce()` 抓屏 → JPEG 质量 55 → `__pushFrame` 灌画布 → canvas 出帧走 RTC。
  实战修正极其密集（无沙箱否则 ICE 永停 new、answer 幂等防 "wrong state: stable"、
  ICE 攒到 answer 落地再喂、candidate 必须 JSON.stringify 成字符串、不放 iceServers 只收 host）。
- **云端中继**：`registry.js rtcSignalToAgent / rtcRelayToViewers / rtcRelayToAgent`，两侧都防回声。
- **管理端收流**：`viewerbackend.cpp:818 kRtcViewerHtml`（离屏 view 挪到 -2000,-2000，
  **不能 hide**——hide 后 Chromium 暂停媒体管线 ontrack 拿不到帧；收流页写 CacheLocation 而非 Temp）。
  抽帧后仍走 `setRtcFrame` 复用 JPEG 通道上屏 ⇒ 与老 JPEG 双路，`kRtcStaleMs` 定优先级。

### 🔴 真根因：后上线的设备永远拿不到 rtc-start（当前版本必现）
用户现场进程：管理端 `Downloads/pkg-0.6.23-rc.1` **12:22** 启动，
被控端 `Downloads/agent-portable-0.6.23-rc.1` **12:33** 启动（管理端先、设备后）。
1. 管理端启动即 `setCurrentUid()` → 发 `subscribe {uid}`；
2. 云端 `index.js:885 case 'subscribe'`：**设备此刻不在线** ⇒ `rtcSignalToAgent` 只记一条
   warn「开关信号没送到设备」⇒ **rtc-start 丢了**；
3. 设备 12:33 上线 → `registry.js:377 autoSubscribeViewers()` 补发，但它只补
   `v.subs.add` + `pushWatchToAgent`，**rtc-start 的补发条件是 `v.live.has(key)`**（:389）；
4. 而 **`v.live` 全仓无人置位** —— `subscribeViewer(ws, uid, live)` 的两处调用
   （`index.js:806`、`index.js:882`）**都只传 2 个参数** ⇒ live 恒空 ⇒ **补发路径是死的**。
⇒ 现场表现：画面能动能刷（JPEG 兜底），但**永远是轮询不是实时**，日志一切"正常"。
**真机铁证**：当前进程（日志 36037 行起）从头到尾只有 `收到云端消息 type=watch`，
`云端要开推流` 全日志仅 1 次、`采集页就绪` **0 次**、`推流已停` 0 次。
被控端只在推 `[agent-qt] 帧#N 推送 ~181KB`（帧#1…#919）。

### ⚠️ 旁证：历史 Discarded 瘫痪（属**更早版本**，勿误判为当前）
- 日志里 `runJavaScript: disabled in Discarded state` **28263 条** +
  `[rtc] tick `（diag **空**）**690 次** + `帧#N 推流帧复用推送`（帧号 26 万+、累计 50GB）。

  而 JPEG 兜底让人看不出问题** —— 这条失败模式当前版本**没有自愈**，属待点单清单项。

## 2026-10-09 · 🔴 生产事故：考试模式白名单导致学校机房反复重启（#88 落地）

用户现场反馈「考试模式改成黑名单制度听不见吗？导致我学校电脑反复重启」。
这是**更早已点单的 #88**，我一直没做 —— 拖到出生产事故才动手，教训记下。

### 根因（两条叠加，第 2 条才是爆炸点）
1. **设计方向错**：考试模式是**白名单制**（"名单之外全杀"）。要安全就必须穷举所有安全进程，
   而 svchost / 驱动宿主 / 杀软 / 机房管控软件穷举不完 —— 少列一个就是蓝屏。
2. **致命 bug：保护名单彻底失效**。`tasklist /FO CSV` 给的进程名是 **`svchost.exe`（带扩展名）**，
   而：
   - `kSystemGuards` 写的是 `"svchost"`（不带）⇒ `contains()` **永远 false**，系统保护一条没生效；
   - 白名单比较前 `a.chop(4)` 剥了 `.exe`，进程名却没剥 ⇒ 白名单也**一条都没匹配上**。
   ⇒ 唯一还拦得住的只剩 `if (pr.pid < 1000) continue;`。
   ⇒ **只要填了任意非空白名单（`m_enforcing=true`），每 2 秒就把所有 PID≥1000 的进程全杀**，
   其中包括大量 PID>1000 的 `svchost` ⇒ **CRITICAL_PROCESS_DIED(0xEF)** ⇒ 蓝屏 ⇒ 重启
   ⇒ 被控端自启 ⇒ 再杀 ⇒ **反复重启**，与现场完全吻合。

### 修法（黑名单 + 不猜名字）
- **语义反转**：`start(minutes, blacklist)` —— **默认谁都不动，只杀老师点名的**。
  配错最多"没杀干净"（fail-safe），绝不可能杀崩系统（白名单是反过来 fail-dangerous）。
  这条是架构铁律，**别再改回白名单**。
- **名字归一化**：新增 `normalizeProcName()`，**双侧**（进程名 + 名单项）都剥 `.exe` 转小写再比。
- **真正的安全闸门**（取代猜名单的 kSystemGuards），全靠**问内核**：
  1. `NtQueryInformationProcess(h, 29 ProcessBreakOnTermination)` —— critical 标记，杀它必蓝屏
  2. `NtQueryInformationProcess(h, 61 ProcessProtectionInformation)` —— PPL 受保护进程
  3. Session 0（服务会话）一律放过
  - ⚠️ **OpenProcess 失败 / 查询失败 ⇒ 一律当受保护跳过**（宁可不杀，不可杀错）
  - 删掉了假的 `pid < 1000` 保护
  - `stelarith-agent-qt` / `taskkill` / `tasklist` 从名单里强制剔除
- **协议**：`exam_mode` 参数 `whitelist` → `blacklist`。被控端**只读 blacklist** ——
  老版本管理端若还在发 whitelist，被控端读到空黑名单 ⇒ 完全不杀（安全的降级方向）。

### 改动文件
