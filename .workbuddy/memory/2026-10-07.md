## 管理端 0.6.12：灵动岛贴左上角 + 输入框绑定循环 + 批量收口

用户直接甩了一张截图：灵动岛展开面板**贴在左上角盖住左栏**，写着「通知 0/1」不动，顶部「0 台在线」。

### 1. 锚点锚在了 Window 上（截图那个现象）

```qml
anchors.horizontalCenter: root.horizontalCenter   // root = ApplicationWindow
```
**ApplicationWindow 继承 QWindow，不是 Item** ⇒ 没有 anchors 体系、没有 horizontalCenter，
赋个 undefined **静默失效**（不报错、不打日志），Item 退回 x=0 ⇒ 从窗口最左边长，正压左栏。
改锚 `parent`（子项进 `contentItem`，它是 Item）。Toast 同样。
**实测探针：`island x=590 parentW=1180`（正中）；修前 x=0。**

⚠️ 好教训：**QML 里"不报错的错"最贵** —— 锚 Window 只是安静地不生效。

### 2. 我 0.6.11 引入的回归：`th: th` 绑成自己

调用点写 `th: th`，QML 右值先在**组件自身作用域**找 `th` ⇒ 自引用 ⇒
真机刷 7 条 `QML InputField: Binding loop detected for property "th"`，
`th` 恒 null ⇒ 用兜底色 ⇒ **亮色下输入框文字仍近白，0.6.11 那件事其实没修完**。
改 `th: root.th`（`CommandPalette` 那处本来就是 `pal.theme`，无事）。
⚠️ 抽组件时，**调用点的属性名不能和目标组件自己的属性同名**，否则绑定自噬。

### 3. 「通知 0/1」不动 = sendAction 不管在线

`sendAction()` 只检查 `currentUid` 非空、**不检查在线**。设备离线时指令发出去没人回执，
`batchStep` 永不推进 ⇒ 灵动岛永远亮着。补两处：① 下发前 `isDevOnline()` 过一遍，离线直接结账不发；
② 窗口层 `batchTimeout` 按台数 10s~60s 收口，到点把剩下的算失败并如实报。

### 1. 画面太小 —— 先量再改

## 02:29–02:50 · P0：考试模式导致教室机蓝屏（BugCheck 0xEF CRITICAL_PROCESS_DIED）

## 04:35-04:55 默认不推流 + 点远控才实时（解决远控闪烁卡顿）

用户：「控制时明显感觉到鼠标闪烁延迟卡顿，非控制页或选中单个设备就不要推流了，默认也不推流，只推图片，点击远控后才可以实时」

根因三条（两条是"推流不该默认开"、一条是采集页自己作妖）：
1. 云端 `index.js:812` 只要收到**任何** `subscribe`（选中设备/进控制页/设备上线自动补订/管理端鉴权后补第一台）
   就 `rtcSignalToAgent(uid,'rtc-start')` ⇒ 被控端一挂就被抓屏 + 拉起 Chromium 采集推实时流，几十台一起卡。
2. 采集页 `cv.captureStream(15)` 让浏览器 15fps 自己抽 canvas，而 `rtcTickOnce` 每 200ms 又整张 `drawImage`
   重画进同一个 canvas ⇒ 两个节奏对不上，**抽到"重画到一半"的帧就是闪烁/卡顿**。
3. 远控时抓两遍屏：`rtcTickOnce` 抓一次（给 canvas）`captureAndSend`（2 秒定时）再抓一次（发云端）
   ⇒ 一秒两次 grabWindow + 两次 JPEG 编码 + 两次 base64 灌页面，压主线程，鼠标发沉。

改法：
- **云端**（改 JS **必须重启 StelarithCloud** 才生效）：
  `registry.js` viewer 记录加 `live:Set<uid>`；`subscribeViewer(ws,uid,live)` 第三参维护；
  `autoSubscribeViewers` 只在 `v.live.has(key)` 时才 rtc-start（原来无条件发）。
  `index.js` subscribe：`live===true` → rtc-start，**否则 rtc-stop**（让"点过远控又切走"一定收敛，不漏停推）；
  unsubscribe 逻辑不变；`onViewerAuthed` 补第一台明确 `live:false`。
- **viewer**：`viewerbackend.{h,cpp}` 加 `live` 属性 + `setLive(on)`（开=先退订→600ms 后重订 live:true；
  不能只发一条 subscribe，云端对已订过的 ws 不重发 rtc-start ⇒ 按钮按了没反应；lambda 里校验 `uid==m_currentUid`
  防这 600ms 内切机器把推流开到上一台）；`setCurrentUid` 开头若 m_live 先退订上一台并把 live 复位；
  订阅 payload 固定 `live:false`。QML：远控开/关都先拨 setLive，`runAction` 里按**动作名**（d.a）再兜一层，
  命令面板/快捷键入口也躲不掉。
- **被控端**：采集页 `captureStream(0)` + `st.tr.requestFrame()`（**必须 drawImage 之后再取帧**，早一毫秒就是上一张）；
  `__reset` 清 st.tr/manual；`rtcTickOnce` 抓的 JPEG **一帧两用**（灌 canvas + 直接发云端），`captureAndSend` 开头
  `if (g_rtcOn) return` 让位（screenshot 动作自己抓屏，不受影响）。

实证（假管理端走 viewer 通道，脚本已删）：
- `subscribe{live:false}` → 被控端无 rtc-start，只有 JPEG 轮询；
- `subscribe{live:true}` → `[rtc] 帧#164..175 推流帧复用推送`（起推流 + 复用生效）；
- `unsubscribe` → `云端要停推流` → `推流已停` → `采集页已回收（Chromium 渲染进程随之退出）`。
本地被控端已升级（备份 `stelarith-agent-qt.exe.bak-20261007-043952`）；云端已重启。

## 2026-10-07（五）日志自动主动上报（被控端 → 云端）

**诉求**：「日志自动主动上报」。现状是日志只落机器本地，机房机器没人去拔盘拷；旧链路只有被动的
`log_tail` 拉（机器不在线时那条指令根本没机会问）。

**做法**：在被控端**唯一日志出口** `appendLogFile()` 末尾接一行 `enqueueLogUpload(line)` →
全库日志自动覆盖，不动任何调用点。环形缓冲 1000 行 + 紧急行（含 FAIL/ERROR/失败/异常/拒绝/错误/断开）
立刻推（2 秒限流）+ 日常 5 秒批量 + 离线只攒不发（重连拿到 `registered` 立刻整批补发）。
**三条约束（写在代码里）**：① 本地先落盘再谈上报；② 离线只攒不发；③ 上报过程
（`g_logUploadBusy` 整段）里新产生的日志**只落盘不排队** —— 否则「已上报 N 行」自己又变一行待上报，永远发不完。
云端新协议 `{type:'log', payload:{lines:[...]}}` → `registry.js` 的 `ingestDeviceLog()` 按 uid 落
`logs/agent-<uid>.log`（串行写链 + 2MB 轮转 + 自己累加字节数），error 级只 pushEvent 一条汇总；
index.js 加 `case 'log'` + 回执 `logged`，并加只读接口 `GET /api/logs?uid=&n=`（并入既有 `isManageApi`，
uid 白名单防路径穿越）。

**实测证据（本机 N7）**：云端 `logs/agent-N7.log` 涨到 276 行 / 24.8KB；
**停云端 55 秒 → 起云端 → 重连补发 39 行**，云端里「云端断开」7 次、「后重试」7 次（断线前基线 0）＝断线补发实锤；
最近 40 行 events.log ERROR 数 0（假 ERROR 已清）；`/api/logs` 五种情况：无令牌 401、正常 200、穿越 400、空 uid 200、n 夹住。

**踩坑（都是实测撞出来的）**：
1. 云端 `logLineLevel` 把「超时」列进 error → 注册回执原文「…超时 30000 ms」使每次注册都甩假 ERROR。
   → 云端去「超时」（保留英文 TIMEOUT），**被控端 `isUrgentLine` 故意保留「超时」**（提前推一次有 2 秒限流兜着）。两端口径不同是刻意的。
2. `qInstallMessageHandler` 不分级别一律落盘 → 每 5 秒的回执行 qDebug 也顺着流到云端，一天上万行。
   → 出口加 `if (type == QtDebugMsg) return;`。**「进不进日志」在出口一次定死。**
3. `disconnected` 三条是 `fprintf(stderr)` → 装机后计划任务拉起**没有 stdout**，断线现场既不落盘也不上报。
   → 全改 `qInfo`。新增直写 stderr/stdout 时先想这条（第 0.6.14 那条老规矩的又一次）。
4. `kLogRingMax` 先给 400 → 退避上限 15s，长断网刷几千行「重试」把**断网那几句**挤掉（那几句最值钱）。
   → 提到 1000 行（≈120KB）。
5. 换 exe 顺序搞反（先换文件再停进程）→ `Copy-Item 正由另一进程使用`。正确：停两端→等 9s→备份→换→起云端→起被控端。
   备份名里塞 `$(Get-Date).ToString('HHmmss')` 报「不支持给定路径的格式」，写死文件名。
6. Edit 手滑多补一个 `}`，靠 `_tmp-brace.py`（剥字符串/注释后统计括号）编译前揪出来。
   临时脚本一律 Write 落盘执行（heredoc 带反斜杠转义必炸）。
7. PowerShell 的 `Get-ScheduledTask … | Select-Object -ExpandState` **不存在**，用 `().State`；

### #90 关机/重启指令会一直发、被控端一直重启 —— 已修 + 云端已重启止血
- **根因（两层）**：
  1. 被控端 `control-qt/src/main.cpp` 原来是**先 `ExitWindowsEx` 关机、再 `sendActionReceipt` 回执** —— 进程一关回执物理上发不出去，云端永远判"未回执"。
  2. 云端 `store.js` 的 `pendingFor()` 把所有 `state='dispatched'` 都当可补发 ⇒ 设备重连再补发 shutdown ⇒ 又关 ⇒ 又死 ⇒ 死循环。现象＝「点一次关机，机器一直重启、被控软件一连上就立刻重启」。
- **修法（云端 + 被控端双保险，缺一层都会在某个版本组合下复发）**：
  - 云端 `store.js`：队列表加 `no_resend` 列（`TERMINAL_ACTIONS` = shutdown/reboot/schedule_shutdown/schedule_reboot/self_update 自动置 1），`pendingFor` / `listPendingAll` 一律 `AND no_resend = 0`；新增 `expireTerminalHistory()` 把**历史遗留**的关机类未回执指令一次性标 expired（只改 schema 拦不住历史数据）。
  - `store.js` 还加了 `migrateTerminalColumn()`（生产旧库 ALTER ADD COLUMN，duplicate 报错即已迁移）与 `isTerminalAction()`。
  - `enqueueDispatch(uid, action, params, noResend?)` 第四参：不传按动作自动判；传 0 用于补录旧行（回归测试要用）。
  - 被控端 `main.cpp`：shutdown/reboot 分支改为 **① 本机去重（`terminalDonePath()` 落盘记录已执行 id）→ ② `markTerminalDone()` → ③ 只排期 `QTimer::singleShot(2500, …)`，回执由第 4206 行统一发出**，顺序反了就白改。启动懒加载 `loadTerminalDone()`（不依赖启动顺序）。
  - 指令入口记 `g_lastInstrId = id`，供 executeAction 去重判定用。
