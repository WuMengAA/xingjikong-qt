## 段 A · 管理端 ICE 方向串路 + 切设备黑屏（viewer-qt，已提交 5cf5350）

### A1. window.__addIce is not a function —— 根因不是"函数没定义"

判断"收流页能不能灌"一直用的是 `if (!m_rtcView)`，这是错的：
`m_rtcView` 在 `initRtcView()` 里 `new QWebEngineView()` 之后**立刻非空**，
但 `page->load()` 是异步的。load 完成前 runJavaScript 是对着 about:blank 执行的，
`window.__addIce` 根本不存在，而 `runJavaScript("window.__addIce(...)")` **静默失败**
—— C++ 侧一个错都收不到。
offer 那半边早就有 `m_pendingOffer` 处理同一件事，ICE 这半边当时漏了。

**修法**：新增 `m_rtcPageReady`（只在 loadFinished 里置 true）+ `m_pendingIce`
（上限 `kMaxPendingIce = 128`，超了丢弃并留日志）。loadFinished 里先补灌 offer、
再按序补灌候选 —— 顺序不能反：`pc` 是 `__setOffer` 里**同步** new 出来的，
反了 addIceCandidate 就会撞上 "pc 还不存在"，JS 侧只记一行 ice-before-pc 然后丢掉。

### A2. 本端/远端 ICE 共用一个函数 → 双向串路

`rtcGotIce()` 同时干两件事，却被两个**相反方向**共用：
- 本端候选（JS `pc.onicecandidate`）→ 被 `window.__addIce` 加给自己，Chromium 静默 ice-FAIL；
- 远端候选（云端 `rtc-ice` 报文）→ 被 `sendEnvelope("rtc-ice")` 原样回发给被控端，
  对端收到自己刚发的候选，回环放大。

**修法**：彻底拆开两个方向
- `rtcGotIce()`（Q_INVOKABLE，JS 调）：**只**发云端
- `addRemoteIce()`（私有，云端报文调）：**只**注入页面，不回发

顺带：云端转发顺序不保证 offer 先到，ICE 抢先原来直接丢弃（"候选平白少一半"），
现在改为懒建收流页 + 入队。

### A3. 切到第二台机器永远黑屏（两个原因叠加）

1. `setCurrentUid()` **不重建收流页**，而 offer 的注入**只写在 loadFinished 里** ——
   第二台机器的 offer 存进 `m_pendingOffer` 后再也没人灌。
   → 抽出 `deliverOffer()`：页面就绪就直接灌，没就绪才暂存。
2. 被控端每次 `rtc-start` 都是 `new RTCPeerConnection()`（见它的 `__startStream`），
   每个 offer 背后是一个**全新 peer**。管理端复用旧 pc 去 setRemoteDescription
   会被 Chromium 判 `called in wrong state`。
   → 新增 JS 侧 `window.__resetPc()`（对称于被控端的 `__reset`），
     `deliverOffer()` 灌之前先拆；新 offer 到达时顺带清掉上一轮残留候选。

### A4. 验证
完整构建 exit 0，`build/viewer-qt.exe` 707,584 B（上一版 703,488）。
未验证：真机链路上「实时」徽标、viewfoot 音量、回执流水三条仍未跑真实数据；
`__resetPc` 与候选补灌只在代码层面推演，没做两端真实联调。

### ⚠️ 三方合并的陷阱：不冲突 ≠ 没丢东西（这次踩了两次）

`git merge-file` 只在**双方都改了同一处**时才报冲突。如果**一侧整段删除、
另一侧没动**，git 判定"不冲突"，直接跟着删。这次被静默吃掉两块，
都是编译期才发现：

1. `#include <QWebEngineView>` + `g_rtcView`/`g_rtcTick`/`g_rtcOn` 声明
   → OOBE 版删了声明、RTC 版保留使用 → 满屏 `C2065: g_rtcView: 未声明的标识符`
2. `qputenv("QTWEBENGINE_CHROMIUM_FLAGS", "--no-sandbox --disable-features=WebRtcHideLocalIpsWithMdns")`
   → 不补这行，Chromium 沙箱让 ICE 收集永远停在 "new"、mDNS 隐藏让内网拿到 .local，
   症状是**画面黑屏且没有任何报错**。必须早于任何 QWebEngineView 创建。

**结论**：三方合并之后必须再做两道核对，不能只看冲突数：
```
git diff --no-index --unified=0 base.cpp  结果.cpp | grep '^-'   # 基线丢了什么
git diff --no-index --unified=0 rtc.cpp   结果.cpp | grep '^-'   # A 侧丢了什么
git diff --no-index --unified=0 oobe.cpp  结果.cpp | grep '^-'   # B 侧丢了什么
```
三份清单逐条过一遍，再编译。

## 段 F（03:00-03:40）：RTC 建不起来的真因 + 两端内存优化

### F1. `m_rtcPageReady` 置位顺序反了（RTC 一直建不起来，静默退回 JPEG）
`viewerbackend.cpp` 的 `loadFinished` 里，原来是 **先** 补灌 offer **后** 才 `m_rtcPageReady = true`，
而 `deliverOffer()` 第一句就靠这个标志决定"直接灌 JS"还是"再存回 `m_pendingOffer`"。
→ 补灌那一下永远判成"页面没就绪"，offer 被原样塞回队列，pc 永远为 null，
候选只能喂给 null pc，日志里只留两行 `ice-before-pc`，画面静默退回 JPEG 轮询（很好骗）。
修：把 `m_rtcPageReady = true` 提到 offer 补灌之前（候选补灌仍排在 offer 之后）。
**验证**：`hasPc:true state:connected tracks:video:live 640x400 21.8fps`。

### F2. 内存优化：无人看时回收 WebEngine（两端对称）
- control-qt：`rtcStop` 里 5 秒没人重新点开就 `deleteLater` 掉 QWebEngineView；
  `rtc_start` 里 `cancelRtcViewReap()`。
- viewer：`releaseRtcView()` / `scheduleRtcViewReap()`，`rtc-stop` 广播与断连各触发一次。
- **兜底触发源（关键）**：不能只靠云端的 rtc-stop 广播 —— 实测管理端被强杀时云端**不补发**。
  两端都加"与云端断开超过 `STE_RTC_IDLE_MS`（默认 20s，0=关）就回收"，
  判据用"跟云端断多久"而不是"多久没收到信令"（后者在画面稳定后会误杀正在看的画面）。
- 踩到的两个坑（都修了）：
  ① 默认值写法 `qgetenv(...).toLongLong(20000)` 编译不过（QByteArray 要 bool*），且
     空串读出来是 0，会被 `if (limit > 0)` 判成"关掉" → 改成 `QString::fromLocal8Bit(...).toLongLong()` + 空串取默认 20000；
  ② **离线起点只认第一次断连**：退避重连失败会反复走 `disconnected`，每次刷新起点 →
     倒计时永远推不完（实测断线 26s、重连失败 3 次没触发过）。
- **实测数字**：推流中两端合计 ≈965MB（agent 438 + 2×Chromium ~240 + viewer 287）；
  断连后 → agent 415MB + **0 个 Chromium**。日志串：`推流已停：与云端断开 3 秒` → `采集页已回收`。
- ⚠️ 架构性上限：agent 回收后私有内存仍有 ~456MB、78 线程 —— 那是 **WebEngine 在 agent 主进程里**的
  Chromium browser 现场，Qt 删掉 view 卸载不掉。再往下只能把 WebEngine 从常驻改成按需加载（改架构）。

## 段 G（内存优化 A1 + A2，2026-10-05 下午）

用户指令：「两端内存占用太大了，优化性能」，我列了 A/B/C 三类目标后用户说「然后开干」，
按建议顺序做了 A1 → A2。**两边都是"顺着段 F 的架构性上限往下压"**，不是新功能。

### G1（A1）被控端离线不抓屏
- 位置 `captureAndSend()` 开头。
- 判据：`g_ws && g_ws->state() == QAbstractSocket::ConnectedState`，不满足直接 return。
- 为什么：抓屏是这条链路**最贵**的一步（grabWindow 跨进程取整屏位图 + 整张压 JPEG），
  而断线时抓到的帧**一帧都送不出去**（`sendBinaryMessage` 对着断开 socket 返回 0）。
  原实现照样每 2 秒抓一张、照样编码，只在最后 `if(online)` 丢掉 —— 日志刷 `帧#N 离线`，
  机房几十台机器一起空转就是这个量级。
- 提前返回必须排在 `grabWindow` 和 JPEG 编码**之前**，否则省不下来（这是本段最容易写错的地方）。
- 留一行心跳：每 30 次（约 1 分钟）打一次「云端不在，跳过抓屏（累计跳过 N 次）」，
  全静默会让"云端挂了"这件事在日志里消失。
- 尾部 `if(online){...}else{...}` 简化为直发（走到那里必然在线）。

### G2（A2）WebEngine 按需加载
- 新增 `ensureWebEngine()`，在 `rtcStart()`（真的有人要看画面）时才拉起 Chromium。
- 省下的是**进程常驻**：Chromium 一旦起过就留在 agent 主进程里（~456MB 私有 / 78 线程），
  Qt 删掉 view 也卸不掉（段 F 已实测）。机房整天没人看画面，这份常驻纯浪费。
- 环境变量（`QTWEBENGINE_CHROMIUM_FLAGS` = `--no-sandbox --disable-features=WebRtcHideLocalIpsWithMdns`、
  `QTWEBENGINE_DISABLE_SANDBOX=1`）从 `main` 开头**挪进** `ensureWebEngine()`：
  Chromium 现在是按需启动，环境变量必须紧贴启动那一刻，放进程开头会与实际时机脱节。
- **⚠️ 坑一（本段最大的坑）：`QtWebEngineQuick::initialize()` 在 Qt6 动态构建 + Widgets 程序里
  运行时调用 → 启动期死锁。** 症状：进程只剩 2 个线程、11MB、不连网络、不写日志、**完全无输出**，
  看起来像"程序没启动"。一度以为是环境变量问题。结论：**这个函数是给静态构建做 pre-link 用的，
  我们不需要调**；运行时的 Chromium 拉起由 `QWebEngineView` 本身触发（Qt 在 WebEngineWidgets
  插件里做了）。CMakeLists 相应**不加** `WebEngineQuick`，并留了注释。
- **⚠️ 坑二：`page->setHtml()` 是异步的。** 刚 new 出来的 view 还在 `about:blank`，
  立刻 `runJavaScript("window.__startStream()")` 会静默抛
  `Uncaught TypeError: window.__startStream is not a function`（C++ 侧**收不到任何错**）。
  以前靠 `rtcTickOnce()` 每 200ms 兜一遍蒙对了，但窗口期里 `__diag`/`__drain` 全空转、首帧晚几百毫秒。
  修复：改到 `loadFinished` 里起第一枪（`g_rtcPageReady` 置位 + 失败时大声 `qWarning`），
  `rtcTickOnce()` 在 `!g_rtcPageReady` 时直接 `return`；新建 view 时 `g_rtcPageReady = false;`。
- 顺带：`kRtcReapDelayMs = 5000` 常量抽出（原硬编码 5000）。

## 段 H（viewer 侧 RTC 建不起来的真因，2026-10-05 傍晚）

段 G 提交后做收尾验证时，**发现云端自愈后 RTC 再也建不起来**。追到根因并修好。

### H1. 症状（很容易被误判成"没问题"）
- 两端都连上云端、业务指令全通（media_list / set_volume 有回执）、
  viewer 也在收 **JPEG 兜底**画面（`画面在动[JPEG]`）—— 看起来"一切正常"。
- 唯独 **RTC 建不起来**：被控端日志 `state:negotiating / err:pc-failed /
  gather:new / conn:new / answeredAt:0 / ss:have-local-offer`，
  `offeredAt` 一直不变（同一个老 offer 无限重发）。

### H2. 定位过程（三条钥匙）
1. **云端 `events.log` 里那两条 warn 是决定性的**：
   - `{"level":"warn","msg":"WebRTC 信令发不出去：设备不在线","uid":"","type":"rtc-answer"}`
   - `{"level":"warn","msg":"WebRTC 信令发不出去：设备不在线","uid":"","type":"rtc-ice"}`
   `uid` 是**空字符串** → 对应 `registry.js` 的 `rtcRelayToAgent`：
   `devices.get("")` → undefined → 「设备不在线」→ answer 被丢。
   （中文 msg 在 PowerShell 里 GBK 解码看着是乱码，但 JSON 字段可读）
2. **云端方向是对的**：`index.js:270`（viewer 发来）走 `rtcRelayToAgent`；
   `index.js:432`（agent 发来）走 `rtcRelayToViewers`。两段互补，不是云端 bug。
3. **viewer 侧 answer 的 uid 取自 `m_currentUid`**（`rtcGotAnswer` / `rtcGotIce`），
   而 `rtc-offer` 分支**只灌 sdp、从不更新 `m_currentUid`** → 这就是洞。

### H3. 根因（两个独立的缺失，缺一即黑）
`m_currentUid` 变成空的途径：
- `refreshDevices()` 收到**空设备表**时会 `m_currentUid.clear()`
  —— 云端重启 / 被控端掉线重连期间设备表会短暂为空；
- viewer 刚启动、设备表还没到的那一刻也是空。

之后 offer 到达 → `rtc-offer` 分支只 `deliverOffer(sdp)`，
**不把报文里的 uid 同步进 `m_currentUid`** → `rtcGotAnswer` 回 answer 时带空 uid
→ 云端丢 → 被控端永远等不到 answer → `pc-failed` 无限重发。

### H4. 修复（commit `0f61c4f`）
`Stelarith-viewer-qt/src/viewerbackend.cpp`，+24 行：
- `rtc-offer` 分支开头：`rtcField(pay,"uid")` 取到就把 `m_currentUid` 修正过来
  （offer 携带的 uid 是"这条协商属于哪台机器"的**权威来源**，比本地设备表可靠）。
- `rtc-ice` 分支同样补一份：**ICE 可能先于 offer 到达**，
  那一刻 `m_currentUid` 同样是空的，不补则本端候选回发 uid 也空。

### H5. 验证（viewer 日志逐条坐实）
- `[viewer] RTC 报文到了 type=rtc-offer len=2780 uid=TEST1 sdp=0 cand=0 payload=2`
- `[viewer] RTC offer 带的 uid=TEST1 与本地当前 uid= 不一致，以 offer 为准修正`  ← 修复生效
- `[viewer] RTC answer 已回云端（sdp 2065 字符 → TEST1）`
- `[viewer] RTC 信令已中继 type=rtc-answer ok=true`  ← 云端收下了

被控端：`state:streaming / gather:complete / ss:stable / answeredAt 非 0`；
viewer：`画面在动[RTC] 22.8 fps`。

### H6. 断连→恢复全链路闭环（顺带把段 G 的 A1/A2 也一起验了）
1. 有人看时 RTC streaming；**kill 云端**（PID 34492）；
2. agent 退避重连（2s→4s→8s→15s 上限），20 秒后日志出现
   `推流已停：与云端断开 20 秒…先收采集页` + `采集页已回收（Chromium 渲染进程随之退出）`；
   **Chromium 归零**，agent 降到 ~231MB；
3. `云端不在，跳过抓屏（累计跳过 31 次）` ← **A1 生效**（断线期间不空转抓屏）；
4. 触发 `StelarithCloudWatchdog` → 云端 04:02:43 自愈（PID 31400）；

### H7. 记账 / 结论
- **本段是 viewer 侧既有缺陷，与段 G 的 A1/A2 无关**（A1/A2 只动 control-qt）。
  它是"云端重启后 RTC 不自愈"的真因；段 F 只修了首次 offer 补灌顺序，没覆盖这条。
