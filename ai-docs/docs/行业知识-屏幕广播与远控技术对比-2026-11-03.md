# 屏幕广播与远程控制技术对比：VNC / RDP / WebRTC / RTMP / RTSP 在「教室集控」里怎么选

> **30 秒电梯演讲**：教室集控里"看学生屏幕"和"把老师屏幕投给学生"是两件不同的事，技术栈完全不同。一对一接管用 VNC/RDP（像素协议）；一对多广播用 RTMP/RTSP（流媒体）；低延迟实时协同用 WebRTC（P2P）。星集控当前走的是 **C++ 端 VNC 帧缓存采集 + `image://vnc/live` 图像提供者的 QML 渲染路线**，把"重活"留在 C++、QML 只画——这正好踩中它的"纯净 UI"红线。本报告把五种协议拆成一张选型矩阵，并 honest 标注哪些是源码确认、哪些是按公开常识推断。

---

## 一、先分清楚：广播 vs 远控 vs 监看

```
┌──────────────────────────────────────────────────────────────┐
│  交互模型                 典型协议            一对 N 形态        │
├──────────────────────────────────────────────────────────────┤
│  一对一接管（远控）        VNC / RDP         1 管理员 : 1 设备   │
│  一对 N 监看（巡课）       VNC + 轮询        1 教师   : 多设备   │
│  一对多广播（投屏）        RTMP / RTSP/Multicast  1 教师 : 全班 │
│  低延迟实时协同            WebRTC            P2P / SFU         │
└──────────────────────────────────────────────────────────────┘
```

> ✅ 星集控的"监看/巡课"是 VNC 路线的多画面轮询（`Stelarith-control-qt/src/` 的 vnc_client / `image://vnc/live` provider）；"屏幕广播"（老师屏→学生屏）在仓库里是**课程表/媒体/通知类的指令下发 + 学生端本地渲染**，并非强制走 RTMP 流——具体广播实现需深挖 `class/` 与 `media/` 域确认（🟡 推断）。

## 二、五种协议速查卡

| 协议 | 传输模型 | 延迟 | 一对多能力 | 穿透/部署 | 典型用途 |
|---|---|---|---|---|---|
| **VNC（RFB）** | 帧缓冲像素差量 | 中（~50-150ms 局域网） | 靠服务端多连接，**非原生广播** | 端口转发/内网 | 远程接管、巡课监看 |
| **RDP** | 协议级图元（非裸像素） | 低-中 | 多会话但每会话独立 | Windows 原生 | Windows 远控、虚拟桌面 |
| **WebRTC** | P2P + SRTP，UDP | **极低（<50ms）** | SFU 可一对多，但带宽平方级 | 需信令+STUN/TURN | 实时互动、低延迟投屏 |
| **RTMP** | TCP 推流 + CDN | 高（1-5s） | **原生一对多** | 推流服务器/CDN | 直播式广播、录播 |
| **RTSP** | 流媒体（UDP/TCP） | 中 | 多客户端拉流 | 内网/专线 | 摄像头直播、监控 |

## 三、各协议展开

### 3.1 VNC（RFB 协议）
- **原理**：远程帧缓冲（Remote Framebuffer），把屏幕当成"像素矩形"差量推送。TightVNC/TigerVNC/RealVNC 各有编码优化（Tight 压缩、H.264 扩展）。
- **优点**：协议简单、跨平台、几乎任何 OS 都能跑；**非常适合"看一眼学生机在干嘛"**。
- **缺点**：**不是为广播设计的**——一个 VNC server 同时喂 N 个 viewer 靠的是服务端逐连接编码，N 大了 CPU 爆；纯像素协议对带宽不友好。
- ✅ 星集控用 VNC 做**巡课监看**是合理选型：一对一/少量并发，延迟可接受。

### 3.2 RDP（Remote Desktop Protocol）
- **原理**：微软协议，传输的是"画圆/写字"这类**图元指令**而非裸像素，所以带宽效率远高于 VNC。
- **优点**：Windows 原生、多用户会话、体验接近本地。
- **缺点**：跨平台支持弱（Linux/macOS 需兼容实现）；商用授权复杂；**不适合"投屏广播"**。
- 🟡 教育场景里 RDP 多用于"管理员接管教师机排障"，少用于学生机集控。

### 3.3 WebRTC
- **原理**：浏览器原生实时通信，UDP + SRTP，**NAT 穿透靠 STUN/TURN，信令走独立通道**。
- **优点**：**延迟最低、画质自适应、天然 P2P**。
- **缺点**：**一对多广播是它最弱项**——P2P 下 N 个接收方 = N 条独立流，带宽随 N 平方涨；要广播得引入 SFU（ Selective Forwarding Unit）中转，成本高。
- 🟡 星集控若有"实时互动投屏"需求，WebRTC + SFU 是方向，但需信令边车（仓库里有 `stelarith-p2p-signaling` skill 提到 P2P WebRTC 信令边车，说明该路线在规划中）。

### 3.4 RTMP
- **原理**：Adobe 推流协议（虽已宣布 EOL 但生态仍在），TCP 推到流服务器/CDN，**原生一对多**。
- **优点**：**广播王者**——一个推流，万人拉，CDN 扛量。
- **缺点**：延迟高（1-5s），不适合"实时互动"，适合"直播式上课"。
- 🟡 适合"名师课堂直播到全校"，不适合"教师实时看学生反应"。

### 3.5 RTSP
- **原理**：实时流协议，常用于摄像头/监控，多客户端可同时拉同一路流。
- **优点**：内网低延迟直播、监控标准。
- **缺点**：公网穿透差、依赖专线/内网。
- 🟡 适合"教室摄像头画面汇聚到管理端"，不适合桌面级集控。

## 四、选型决策树（教室集控视角）

```
你到底要什么？
   │
   ├─ 看学生机在干嘛（巡课）────────────▶ VNC（已用 ✅）
   ├─ 接管一台设备排障─────────────────▶ VNC / RDP
   ├─ 老师屏 实时 投给全班（互动）──────▶ WebRTC+SFU（🟡 规划中）
   ├─ 名师课 直播 到全校（非实时）──────▶ RTMP/CDN
   └─ 教室摄像头 汇聚监看───────────────▶ RTSP
```

## 五、Stelarith 路线对照（✅ 一级信源）

- **监看/巡课**：`Stelarith-control-qt` 的 VNC 客户端 + `image://vnc/live` 图像提供者，QML 侧只 `Image { source: "image://vnc/live" }` 渲染（✅ 符合 §10.9 纯净 UI：C++ 取帧、QML 只画）。
- **媒体/课表/通知下发**：走云端指令 + 设备本地渲染（✅ `src/island/`、`src/ota/`），非流媒体。
- **WebRTC 信令**：仓库 `stelarith-p2p-signaling` 路线在规划（🟡，需信令边车 + TURN 公网穿透）。
- **广播（RTMP）**：源码中未见明确 RTMP 广播实现（❓，待 `media/` 域深挖）。
