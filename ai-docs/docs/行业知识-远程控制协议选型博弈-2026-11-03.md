## 0. 先破一个迷思

> **「远控 = TeamViewer」是消费级错觉。**
> 教室集控的远控，约束完全不同：
> - 设备在被 NAT / 学校防火墙 / Cloudflare 隧道**后面**；
> - 机器是**老旧 Windows 机型**（i3 / 4G 内存常见）；
> - 管控要求**可审计、可自托管、可录制**；
> - 网络是**教育网出口**，延迟抖、带宽挤。
>
> 所以选型不是「哪个最快」，而是「哪个在**最烂的条件下仍能稳**」。

## 1. 四方擂台（ASCII 对比矩阵）

```
  维度          RDP           VNC/RFB        WebRTC          PPPoE/裸TCP
  ──────────────────────────────────────────────────────────────────────
  穿透 NAT     弱(需网关)     弱(需端口)    强(P2P+信令)    最弱
  穿透隧道     中             强(可套WS)    强(可套WS)      中
  延迟         低             中            极低            中
  带宽占用     中             高(全帧)      低(差量)        高
  老旧机性能   中(软解码重)   低(CPU编码)   高(需H.264硬编) 低
  跨平台       弱(微软系)     强(全平台)    强              强
  自托管难度   高(授权)       低            中(需信令+STUN) 低
  可审计/录制  弱             强(帧可截)    中              强
  国产化适配   弱             强            中(依赖浏览器)  强
  ──────────────────────────────────────────────────────────────────────
  我们的选择   ✗              ★基座         推流备选         ✗
```

> 读矩阵结论：**没有完美协议**。RDP 快但锁生态；WebRTC 极快但吃硬件+浏览器；
> VNC/RFB 慢但**无处不在、可套 WebSocket、可自托管**——在「最烂条件」下它最稳。

## 2. 我们的定式：RFB-over-WS（把 RFB 塞进 WebSocket）

```
  传统 VNC：    教室机:5900  ←── 直连 ──→  管理端
                ❌ 学校防火墙挡、NAT 后不可达

  我们的形态：  教室机 ──RFB帧──▶ 本地 WS 客户端
                          │
                          ▼
                     Cloudflare 隧道 :8788 (wss://)
                          │
                          ▼
                    云端中转 ──▶ 管理端/老师机
                ✅ WebSocket 是穿透隧道最稳的通道
```

**为什么是 WebSocket 而非裸 TCP**：
- Cloudflare 隧道 / 学校出口对 **HTTP/HTTPS/WS** 放行，对裸 TCP 端口几乎全封；
- WebSocket 升级握手走 443，天然穿透；
- 一条 `wss://` 既能传远控帧，也能传**指令/回执/OTA/心跳**——**协议复用，少开端口**。

**为什么是 RFB 而非自研帧格式**：
- RFB 是 1998 年的老协议，**实现极简**（握手 + 帧缓冲编码 + 键鼠事件）；
- Qt 有现成 RFB 解析能力，我们**用 Qt 原生解析而非塞 WebEngine**（见 `WebRTC去WebEngine接线方案`）——省一个 Chromium 内核 = 教室机少 300MB 内存 + 启动快一倍；
- 帧可截、可录制、可审计——契合管控诉求。

> 创意命名：**「给教室机装一个会翻墙的 VNC」**——本质就是 RFB 穿上了 WebSocket 的外套。

## 3. 为什么没选 WebRTC（以及何时会选）

```
  WebRTC 优势：差量编码 + H.264 硬编 → 1080p 60fps 仅几 Mbps
  WebRTC 代价：
    ① 必须信令服务器(PEER/STUN/TURN) → 架构复杂度 ↑
    ② 依赖浏览器或 libwebrtc(重，~30MB+) → 与「去 WebEngine」哲学冲突
    ③ 老旧教室机无 H.264 硬编 → 软编 CPU 爆炸
  ─────────────────────────────────────────────
  结论：当前机房条件下，WebRTC 的「快」被「重 + 不稳」抵消。
```

> 我们的**演进路线**（`WebRTC去WebEngine接线方案` 实读）：把 WebRTC 当作**推流备选**而非主远控——
> 用于「老师机演示给学生机大屏」这类**单向广播**场景（只需下行、不需键鼠回传），
> 此时 WebRTC 的差量编码优势最大化、信令复杂度最小化。
> **主远控仍是 RFB-over-WS**，因为它在所有教室里都跑得起来。

## 4. 行业里的协议战争（横向知识）

```
  年代    主流远控协议        代表产品            时代约束
  ───────────────────────────────────────────────────────────
  1990s   VNC/RFB            RealVNC/VNC         Unix 多机共享屏
  2000s   RDP                微软远程桌面          Windows 统治 + 域环境
  2010s   商用私有协议        TeamViewer/AnyDesk   NAT 普及 + 消费远程
  2015s   WebRTC             Google Meet/DietPi   浏览器即平台 + P2P
  2020s   RFB-over-WS        ★星集控/类方案       隧道化 + 自托管 + 管控
  ───────────────────────────────────────────────────────────
```

> 创意洞察：**每一代「主流远控协议」都是对上一代「部署痛点」的回应**。
> RFB-over-WS 是对「TeamViewer 式中心化私有 + 无法自托管 + 无法审计」的回应——
> 它把最老协议的**最简单实现**，装进最现代通道的**最强穿透力**，反而最适配管控场景。
> 这恰印证 RustDesk 的成功逻辑：**远控不需要最新协议，需要最稳的部署**。

## 5. 安全博弈（诚实标 🟡）

| 风险面 | RFB-over-WS 应对 | 状态 |
|---|---|---|
| 传输加密 | `wss://` TLS 1.3 端到端 | ✅ 隧道层已加密 |
| 设备鉴权 | 云端令牌 + 设备 uid 绑定 | ✅ `CLOUD_WS_TOKEN` 64 字符强随机 |
| 指令伪造 | 云端签名 + 回执闭环 | ✅ 设备真实执行回执 |
| 录屏合规 | 帧可截可审 | ✅ 契合等保🟡 |
| 横向移动 | 单设备令牌隔离 | 🟡 需核对越权边界 |

> 行业铁律：**远控是教学管理的刀刃，也是攻击面最大的刀刃**。
> 我们的「云端中转 + 令牌 + 回执」三段式，本质是把「谁能控这台机器」的裁决权
> 收归云端，而非散落在每台机器的本地密码——这是集控相对单机远控的**安全范式升级**。

## 6. 一句话收尾

> **选 RFB-over-WS，不是因为它最新，而是因为它在「最烂的教室网络 + 最老的机器 + 最严的管控」三重约束下，是唯一还站得起来的那一个。**
> 协议选型没有银弹，只有**对约束的诚实**——我们把这份诚实写进了隧道草案和去 WebEngine 方案里。
