## 0. 一句话定位（我们到底在哪一格）

```
        教室集控（Classroom Management & Control）
        ─────────────────────────────────────────
        不是「远程桌面工具」，不是「电子班牌」，不是「教学 SaaS」。
        是这四者的**交集**上长出来的一层：

           设备统一管理(UEM/MDM)  ×  数字标牌(Digital Signage)
                                ×  远程协助(Remote Assistance)
                                ×  课表驱动自动化(Schedule-driven Automation)

        我们的形态：教室机 Windows 受控端 + 老师机管理端 + 云端中转(8788)
                   三端用同一套云端协议，UI 层按端选型（桌面 Widgets / 移动 QML / 网页）。
```

> 记忆锚点：用户原话「**主要是代替** ClassIsland」——我们的目标不是「又一个教学平台」，
> 而是**协议级对齐后的开源替代**（闭源集控 → 可自托管、可审计、可改造）。

## 3. 技术谱系（三棵树，讲清我们站在哪根枝上）

### 3.1 设备管理谱系：MDM → EMM → UEM

```
  MDM (Mobile Device Management, ~2000s)
   └─ 管「设备」：注册、配置、擦除、应用分发
        │
  EMM (Enterprise Mobility Management, ~2010s)
   └─ MDM + MAM(应用) + MCM(内容) + 容器
        │
  UEM (Unified Endpoint Management, ~2020s)   ← 我们在这里
   └─ 桌面 + 移动 + IoT + 物联网终端 统一管
        ├─ 教育场景别名：教室机集控 / 电子班牌管理
        └─ 我们的实现：云端令牌 + 被控端心跳 + OTA 渠道晋升
```

> 创意类比：**MDM 是「给每台手机装管控」；UEM 是「给教室里所有带电的东西发号施令」**。
> 我们不做手机（那是 viewer 手机伴侣 App 的事），做的是**教室里的 Windows 受控端**这一种端点。

### 3.2 远程控制协议谱系（我们选了 RFB-over-WS）

```
  RDP (微软)        ── 紧耦合 Windows、需账号体系
  VNC / RFB         ── 跨平台、无状态、协议简单     ← 我们的基座
   └─ RFB-over-WS   ── 把 RFB 帧塞进 WebSocket     ← 我们实际用的（穿透 Cloudflare 隧道）
  WebRTC            ── 低延迟、P2P、需信令         ← 我们「去 WebEngine」后的推流备选
  纯 SaaS 远控      ── TeamViewer/AnyDesk/RustDesk  ← 竞品，无教学语义
```

> 决策要点（仓库实证的）：用 **RFB-over-WS** 而非裸 VNC，是因为教室机在 NAT/隧道后，
> WebSocket 是穿透 Cloudflare 最稳的通道；用 **Qt 原生 RFB 解析**而非塞 WebEngine，
> 是为了低端教室机性能与包体（见 `WebRTC去WebEngine接线方案`）。

### 3.3 课表驱动自动化谱系（事件总线范式）

```
  课表数据源(ClassIsland 档案/学校排课系统)
        │
  课表归一化(Normalize)  ── 我们已建 ScheduleEventBus
        │
  ┌─────┼──────────┬───────────┐
  ↓     ↓          ↓           ↓
上下课  当前/下节  倒计时边界   考试模式
提醒    科目预判    自动计算      自动杀进程
(provider) (自动化条件) (灵动岛面) (exam_mode)
```

> 这一点是**我们相对 ClassIsland 的架构优势之一**：课表不是「一张显示表」，
> 而是**一条事件总线**，上游任何变动都会扇出到提醒/自动化/灵动岛/考试模式四面。

## 4. 竞品解剖（卡片式）

### 🃏 希沃 seewo / 鸿合 HiteVision
- **位置**：交互智能平板（IWB）双龙头，硬件 + 封闭生态。
- **强**：渠道下沉到县乡、售后网点、教师培训体系；设备即入口。
- **弱**：跨品牌管控弱（只管自己家屏）、课表/自动化靠自家 OS、不开源。
- **我们的机会**：学校往往是**多品牌混装**（希沃屏 + 非希沃 PC + 班牌），
  统一管控层是硬件厂商不愿做的「苦活」。

### 🃏 ClassIsland（开源集控，我们的头号对标）
- **位置**：单机 Windows 集控，组件化主界面，**开源**。
- **强**：三层可组合性 = **组件(UI单元) × 提醒提供方(事件源) × 自动化(条件→动作)**；
  插件市场、配置方案(Profiles)、外观全参数化。
- **弱**：**纯单机**、无云端、无多租户、无跨设备下发。
- **我们的差距**（仓库 `ClassIsland功能对标清单` 实读结论）：
  - 我们只有「中层影子」：`provider_registry` 8 提供方、`automation_engine` 3 类触发；
  - 最上层的「组件化主界面」和最下层的「组件级样式覆盖」基本空的。
- **我们的反超点**：提醒提供方**二级结构**（提供方→通道）比它严；考试模式**真杀进程**；
  云端集控闭环（多租户/课表下发/回执/OTA 渠道晋升）它完全没有。

### 🃏 ClassIn / 钉钉教育 / 飞书教育
- **位置**：教学 SaaS，强在「人与内容」，弱在「设备」。
- **判断**：不是直接竞品，是**互补层**——它们管「课」，我们管「机房/教室设备」。

### 🃏 海外课堂管理：LanSchool / NetSupport School / Apple Classroom / Google Classroom
- **LanSchool/NetSupport**：局域网课堂管理祖师爷（屏幕轮巡、禁网、提交作业）；
  架构老（C/S 或局域网广播），**无现代云端、无课表驱动**。
- **Apple/Google Classroom**：绑定自家生态，国内不可用/不适配。
- **共同点**：都**没有「灵动岛式」的常驻信息枢纽**这一形态——这是我们的原创切入点。

### 🃏 RustDesk（开源远控）
- **位置**：TeamViewer 的开源替代，证明「远控也可以开源自托管」。
- **借鉴**：它的成功印证了我们的总路线——**闭源 SaaS 管控 → 开源可自托管替代**是对的。

## 5. 我们的差异化打法（决策树，为什么这么选）

```
                        教室集控该怎么造？
                              │
            ┌─────────────────┼─────────────────┐
            ↓                 ↓                 ↓
       UI 层怎么选？    枢纽长什么样？     升级怎么发？
            │                 │                 │
   桌面 Widgets        灵动岛(Dynamic         OTA 渠道晋升
   + 移动 QML          Island 隐喻)           (alpha→beta→stable)
   + 网页             = 唯一信息枢纽          读时计算、无需重启
            │                 │                 │
   理由：分层原则        理由：8 域依赖          理由：教室机不能
   「同逻辑三端             岛是唯一交叉点             停机升级，
   共享，UI 按端             通知/课表/倒计             渠道灰度降级
   选型」(见手机端设计)      时/天气都汇于此           零风险
```

### 5.1 为什么是 Qt 而非 Web / Electron
- 教室机是 **Windows 老旧机型为主**，Electron 包体 + 内存吃不消；
- Qt 6.12 LTS（2026-09-30 发布，5 年维护）长期可维护；
- 同一套 C++ 业务逻辑三端复用（被控端/管理端/手机），UI 层才分 QtWidgets / QML。

### 5.2 为什么「灵动岛」是枢纽而非普通通知栏
- 仓库事实：`IslandRoot.qml` 是**唯一枢纽**，8 个域依赖它；
- 它把「概览 / 今日课表 / 媒体 / 笔 / 设置 / 自定义 / **日期周次面 / 倒计时面**」收进一个常驻胶囊；
- 隐喻来自手机 Dynamic Island——**小面积、高信息密度、常驻不抢戏**，正好适配教室大屏「边角信息位」。

### 5.3 为什么 QML 纯净 UI 是铁律（§10.9）
- 规则：QML 只画图 + 收点击；网络/JSON/Win32/DB 全在 C++。
- 收益：QML 无编译期检查 → 把脏活锁在 C++，QML 层**不会因业务逻辑出错而整页崩**；
- 代价：每加一个 C++ 注册模块，探针壳必须同步链上（踩过整页空白零报错的坑）。

### 5.4 为什么 OTA 渠道晋升是「读时计算」
- `ota.js` 每次请求 `readFileSync('ota-builds.json')` **无内存缓存**；
- 晋升门槛（5h/24h）是纯函数按 `now - publishedAt` 现算；
- 改文件即生效，**无需重启云端**——守「生产进程不随便重启」铁律。

```
 2000─2010        2010─2015       2015─2020        2020─2022        2022─2024        2024─2026
  多媒体教室  →  交互智能平板  →  录播/班牌普及  →  疫情线上爆发  →  教育新基建+   →  AI+国产化+
  投影+中控       IWB 上墙       电子班牌        直播/SaaS教学    信创替代        集控智能化
```

## 7. 法规与合规（诚实标 🟡：待联网补证）

| 主题 | 与我们相关性 | 状态 |
|---|---|---|
| **未成年人保护 / 防沉迷** | 教室机管控学生机、录屏——涉及未成年人数据 | 🟡 需核对《儿童个人信息网络保护规定》最新修订 |
| **教育 App 备案** | 若面向学校分发管理端 App | 🟡 需核对教育部备案清单口径 |
| **等保 2.0** | 云端中转 8788 属「信息系统」 | 🟡 需确认定级与测评要求 |
| **数据出境 / 国产化** | 自托管云端的优势项 | ✅ 我们「可自托管」天然契合信创要求 |
| **GDPR / COPPA**（若出海） | 当前国内为主，暂不涉及 | ❓ 待定 |

> 创意提醒：**合规不是负担，是壁垒**。ClassIsland 类单机工具天然「不碰数据出境」，
> 但一旦做区域级集控，「等保 + 未成年人保护 + 备案」三件套就是小玩家过不去的门槛——
> 而我们「自托管 + 开源可审计」恰好把合规做成卖点。
